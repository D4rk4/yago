## Abstract

YaGo v0.0.31 makes web discoveries reach the crawler again. Provider rows pass
two filters: one decides whether a page answers the query, the other applies
what this caller asked to be served -- an include or exclude domain, an excluded
term, an inurl. Crawl seeding took the rows that survived both, so a request
narrowed to one host discovered nothing, silently, because an empty seed list
reads in the journal exactly like a provider that returned none. Seeding now
takes the rows verified against the query and ignores the caller's own
constraints, which never said anything about whether a page is worth having.

## Changes

### Crawl seeding is no longer narrowed by the caller's own filters

A provider answer passes `verifiedWebResults`, which does two separate things.
`resultsMentioningTerms` keeps the rows that answer the query; that is
relevance, and a row an engine padded its answer with is not a discovery.
`resultsMatchingConstraints` then keeps the rows this caller asked to be served:
include and exclude domains, excluded terms, an inurl.

Both searchers seeded from the result of the pair. The second half is the
caller's own filter and says nothing about whether a page is worth crawling, so
a request narrowed to a single host discovered nothing at all -- and reported
nothing, because the seeder receives an empty list in that case and an empty
list is indistinguishable in the journal from a provider that returned none.

The two halves are now separate. `relevantWebResults` is what seeding takes;
`resultsMatchingConstraints` still narrows what is served. Both the fallback and
the parallel searcher were changed: they keep their own copy of the seeding
decision, and a node with web fallback set to `always` runs the parallel one.

## Compatibility

- No environment variable, Admin setting, route, request field, response field, public schema, listener, port, service, image name, package path, Bleve mapping, document encoding, storage format, or deployment topology changes. No contract or wire-format change. No dependency change.
- Served results are unchanged. Only the set handed to crawl seeding changes, and only in the direction of seeding more: rows that answer the query but fall outside the caller's include or exclude domains, excluded terms, or inurl are now discovered. Rows that do not answer the query are still never seeded.
- A node that seeds crawl from web discoveries will submit more crawl orders than v0.0.30 did for constrained requests. The per-order depth and page bounds, the live `web.fallback.seed_crawl` toggle, and the seed admission ceiling are unchanged, so the added volume stays inside the limits already configured.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.31 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.31`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify the exact version, `/health`, `/ready`, configured listeners, and current logs. On an index of this size the vault word filter is built before the listeners open; on the reference deployment that has taken 520 and 590 seconds, and readiness should be polled rather than assumed.
5. Start `yago-crawler` after node readiness. Verify its exact version, control and ingest connections, a current heartbeat, and absence of repeating lease-loss output.
6. Keep production verification observation-only.

For rollback, stop crawler and node, reinstall the v0.0.30 package, start and verify the node, and then start the crawler. No index rebuild or data restore is required; no storage format changed in either direction. The older release resumes narrowing discoveries by the caller's constraints, so a constrained request stops seeding again.

## Verification

- `make verify` on the release tree: tidy, format, vet, lint, architecture, race tests, build, and coverage at exactly 100 percent of statements in all six modules (`yagonode` 46910, `yago-crawler` 12051, `yagocrawlcontract` 1265, `yagomodel` 923, `yagoproto` 517, `yagoegress` 59).
- Mutation testing: seeding from the constrained set again in either searcher, and dropping the relevance half from what seeding takes, each fail a test.
- The first version of this change removed both halves, and the existing `TestFallbackDropsUnrelatedProviderResultsAndSeedsOnlyVerified` refused it: under a query for one subject it would have seeded an unrelated row an engine returned. That contract is what split the change into two halves rather than one.
- The new test was itself corrected twice. It first read the seeder's URLs after waiting for the first seed call, which races the second because seeding is spawned per URL; it now polls under the stub's mutex and was run twenty times. It then covered only the fallback searcher, so the mutation against the parallel searcher survived -- and the parallel searcher is the one a node runs with web fallback set to `always`. A sibling test covers it.
- Diagnosis evidence from the reference deployment, read through the records v0.0.30 made visible: for one query `bing` fetched 10 rows and accepted 10 while zero crawl seeds were published; for another, three engines each fetched 10 and accepted none, which is the relevance half working. The provider was answering; the seeding was not.
- Pinned Dockerized scanners. Semgrep 1.168.0 `scan --config auto --error`: clean. Trivy 0.72.0 filesystem scan for HIGH and CRITICAL vulnerabilities, secrets, and misconfigurations: clean. Trivy image scans of the built `yago-node` and `yago-crawler` images: both clean.
- Local Docker live lifecycle gate: `TestIndependentServiceRestartsRecoverCrawlerSessions` passed against images built from this tree.
- Release issue review: no open issues in the repository.

## Known limitations

- `TestSizeSeedAdmissionKeepsTheLargestRequest` is not safe to repeat inside one process: it sizes a package-level admission once, so `go test -count=10` on that package fails on the second run. `make verify` runs each package once and is unaffected. The test's isolation is not fixed here.
- Seeding still reports nothing when it seeds nothing. An empty seed list, a closed live toggle, and a URL skipped because it is already stored are all silent, and telling them apart still requires reading the code rather than the journal. This release removes the cause found by that reading; it does not add the record that would have shown it.
- The provider failures v0.0.30 made legible remain unfixed: on the reference deployment `mojeek` fails with a backend error and `brave` reports rate limiting, while `bing` and the DuckDuckGo engines answer. Web discovery therefore depends on a subset of the configured engines.
- The corpus-signal refresh, the peer-roster write contributors from v0.0.27, and the two deferred fingerprint-read reductions from the v0.0.29 memo are all untouched.
