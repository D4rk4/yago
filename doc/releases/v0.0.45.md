## Abstract

YaGo v0.0.45 corrects cold local-search timeouts that remained after v0.0.44. At node startup, fragmented Bleve shards now pass the existing storage-reserve admission and consolidate one shard at a time before serving; ordinary healthy queries request only the visible candidate count and expand once only when a missing stored document exposes an unseen tail. Disposable 800,000-document gates preserved document totals and brought synchronized cold bursts within the exercised 1.8-second budget. The stored format, mappings, APIs, settings, and deployment topology are unchanged. The first startup can take additional time and temporary disk space; insufficient headroom refuses startup without replacing valid source snapshots. Rollback to v0.0.44 is format-compatible.

## Changes

### Bound persisted segment fan-out before serving

Production v0.0.44 held 559,387 searchable documents in eight Scorch shards. The active index occupied 2,718,265,025 bytes and exposed 69 zap segments, with eight to ten segments per shard. One new common query exhausted the local-search budget while the process incurred 11,240 minor faults, no major fault, and no physical read; its immediate repeat completed in 95 milliseconds. The remaining cold cost was traversal of file-backed mmap pages across the persisted segment fan-out.

Before a disk index becomes available, the node now reads every shard's live document and root file-segment totals. A shard above one segment per 100,000 documents makes the complete current index footprint the required temporary-growth amount and passes it through the established filesystem-reserve admission. Insufficient headroom or a failed measurement refuses startup before a merge begins.

Eligible shards force-merge one at a time. The planner retains the established 100,000-document output ceiling. Every completed merge is reinspected, and the live document total must remain unchanged. A planner that cannot reach the preferred total may stop only within a hard fallback of one segment per 50,000 documents. A larger stalled total, cancellation, a changed document total, or an operational failure refuses startup. Shards already within the preferred bound perform neither storage preflight nor merge work.

The work runs before listeners open, so public search and crawl ingest cannot compete with it. Scorch retains its own valid snapshots during the operation. The index mapping, writer generation, shard routing, segment format, and document store remain unchanged.

### Request only usable candidates on the healthy path

Ordinary disk search previously asked Bleve for four times the visible candidate count on every request. That tail allowed a missing stored document to be replaced without another Bleve call, but healthy indexes paid the scoring and collection cost even when every requested candidate existed.

The initial request now asks for exactly the visible candidate count, bounded by the existing 1,000-hit and corpus limits. If all candidates exist, that page is returned without another Bleve call. One fourfold bounded retry occurs only when the first page contains a confirmed orphan and Bleve reports an unseen result tail. An orphan with no tail does not retry. Retry cancellation and operational failure remain search failures. Facet and post-filter scans keep their independent complete-search bounds.

Stored-document authority, orphan cleanup, total calculation, result ordering, candidate projection, snippets, phrase and proximity evidence, filters, facets, ranking inputs, and public response shapes retain their established behavior.

### Record the read-capacity boundary

ADR-0067 records segment and candidate read-amplification bounds as single-process efficiency and safety rules. Per-process admission remains overload protection; it is not evidence that one replica can satisfy every corpus and burst. Corpus shape, persisted bytes, CPU allocation, queue time, and the complete response pipeline remain part of capacity validation.

Deployments that require hundreds of simultaneous searches within one response budget must provide enough independently validated read capacity to keep every process below its measured cold synchronized bound. This release does not add a replicated-read runtime boundary. Such a boundary requires a separate ADR and synchronized Docker, systemd, and package topology before implementation.

The release gate also inspected all 68 numbered ADRs and their index entries. There are 64 live accepted decisions, three records explicitly superseded by later decisions, and the non-decision ADR-0000 proposal template. The previously queued post-open RWI filter work in ADR-0063 remains implemented and covered. No accepted or queued ADR implementation remains knowingly outstanding.

## Compatibility

- YaCy wire endpoints, Tavily-compatible endpoints, public response shapes, crawler contracts, stored documents, vault routing and shard formats, Bleve mappings and generation markers, package paths, image names, ports, listeners, services, and deployment topology are unchanged.
- No environment variable, Admin setting, default, navigation item, shelf row, Prometheus series, systemd unit, Compose control, dependency, or runtime service boundary changes.
- Bleve remains pinned to v2.6.1 with zapx v17.2.3 and writer generation v2. A fragmented healthy index is merged in place before serving; an already bounded healthy index is unchanged.
- Upgrade from v0.0.44 and rollback to v0.0.44 are format-compatible. A rollback can open the consolidated segments without a document rebuild. It restores unconditional fourfold candidate requests and no longer reasserts the startup segment bound.
- The first start after upgrade may remain unavailable while fragmented shards consolidate. Storage reserve is checked before writing. A refusal leaves valid source snapshots in place and requires additional headroom or rollback before service can start.
- DDGS provider policy remains admin-opt-in. This release does not enable it by default or change engines, request syntax, result admission, crawl seeding, or human-facing provenance.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.45 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.45`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Allow additional time for one-time segment consolidation before listeners open. Wait for exact v0.0.45 identity, health, readiness, stable restart count, and bounded logs. Verify the indexed document total, then exercise several never-before-used common queries before repeating them so acceptance covers both cold and warm paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm a new logical session, continued crawl and index progress, DDGS behavior under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.44, stop both services, install the exact published v0.0.44 package, and start the node before the crawler. The consolidated index is in the same writer generation and segment format, so no rebuild is expected. The v0.0.44 fragmented-read and unconditional-overfetch behavior can return as ordinary ingest creates later segments. Rollback to v0.0.38 retains the generation-v2 boundary and follows the complete derived-index rebuild procedure documented by v0.0.41.

## Known limitations

- Production success remains unconfirmed until the published v0.0.45 Debian package is deployed, startup consolidation completes, and multiple genuinely cold common queries complete within the fixed interactive budget before the crawler is started.
- Ordinary ingest can create new segments after startup. A later restart reasserts the bound; this release does not add online consolidation scheduling controlled by interactive demand.
- First-start duration and temporary growth depend on the existing index. The node checks the complete current footprint against the filesystem reserve, but operators must plan downtime for the admitted merge.
- Synthetic burst results describe the exact corpora and CPU allocations exercised. They are not a universal hundreds-request guarantee. A deployment requiring that SLO needs independently measured horizontal read capacity and a future accepted topology ADR.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class. They do not add a general decoder allocation bound for arbitrary current-generation corruption; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
