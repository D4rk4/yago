## Abstract

Yago v0.0.55 removes index mutation from local-search reads. Production v0.0.54 returned eight cold local-only queries as incomplete and deleted 361 Bleve identities while serving them. Candidate and evidence retrieval had treated missing stored documents as synchronous delete requests, coupling deadline-bound reads to Scorch persistence and merges. Search now filters missing documents without indexing, deleting, or queuing a mutation; explicit lineage removal and full rebuild remain reconciliation boundaries. A disposable production-index copy completed the same terms in 11.220–54.447 milliseconds with stable index statistics. APIs, formats, settings, and topology are unchanged; no rebuild is required. Horizontal capacity for hundreds of simultaneous requests remains separate and unimplemented. Production acceptance still precedes crawler startup.

## Changes

### Keep local search observation-only

Production acceptance of v0.0.54 did not recover local search. Eight genuinely new local-only terms returned HTTP 200 with incomplete availability, zero visible rows, and `local search deadline exceeded` after 1.955 to 2.093 seconds. During those reads the Bleve document total fell from 557,517 to 557,156, then remained stable after the requests stopped. Memory stayed near 500 MiB and the node recorded no cgroup memory pressure or OOM event.

Candidate and evidence retrieval checked whether each Bleve identity still had an authoritative stored document. A missing document was correctly excluded from the visible answer, but the request then synchronously called the ordinary single-document Bleve deletion path. One search could therefore discover many historical or crash-created identities and turn a latency-sensitive read into Scorch mutation, persistence, and merge work. Current document lifecycle operations already own normal index removal, while the operator-triggered full-index rebuild reconstructs derived Bleve state from the authoritative document store.

Candidate retrieval, one-document evidence hydration, and document-set evidence hydration now remain read-only. A missing stored document is still filtered and cannot become visible. The bounded result estimate and established continuation-page behavior remain intact, but no search phase indexes, deletes, or queues a Bleve mutation. Explicit document-lineage deletion continues to remove current documents. Historical drift remains eligible for the existing document-backed full-index rebuild.

Permanent tests hold the Bleve mutation lock while searching a missing candidate and require the search to complete. Missing and present candidate paths, individual evidence hydration, and document-set hydration must leave both the indexed document total and `UpdatedAt` unchanged. Existing negative tests continue to prove that a legitimate empty answer is not reported as an infrastructure failure.

A disposable full copy of the production Bleve tree supplied the production-shaped check. A diagnostic presence source rejected every candidate for the same eight terms that failed on v0.0.54. Their bounded searches completed in 11.220 to 54.447 milliseconds, while index statistics remained exactly 559,321 documents with an unchanged update time. The diagnostic source was removed after the test. Candidate code never opened live production data.

ADR-0076 records the observation-only boundary and amends ADR-0066 and ADR-0073. FTR-201 records the implemented behavior; FTR-053 and FTR-191 now identify explicit lineage deletion and full-index rebuild as the reconciliation owners. The release audit matched all 77 numbered ADR files to 77 unique index targets. Seventy-three live decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision template. The previously delayed ADR-0063 remains implemented by FTR-187's bounded post-open word-filter maintenance and its bidirectional and lifecycle tests. No accepted or queued ADR implementation remains knowingly outstanding.

Hundreds of simultaneous deadline-bound requests remain a horizontal capacity requirement rather than a claim about one four-processor process. A future read tier must provide each replica with independent processor and I/O capacity, an independently owned immutable search generation, and a query-ready document projection. Routing must admit only ready replicas within the freshness bound, include queue time in the latency objective, and retain the target with one replica unavailable. Multiple processes must not share one live mutable Scorch directory. That runtime topology requires a separate accepted and implemented ADR with synchronized Docker, systemd, package, rollout, and rollback changes.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.55 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.55`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.55 identity, health, readiness, indexed document total, stable restart count, bounded logs, and resource counters. Exercise genuinely new sequential local queries and synchronized result-bearing probes while verifying that the index total remains stable across reads.
5. Start `yago-crawler` only after node search acceptance passes. Confirm its Connected state and new logical session, then prove manual and web-ingest crawl-order progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.54, stop both services, install the exact published v0.0.54 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores the search-triggered deletion behavior that this release removes.

## Known limitations

- Production success remains unconfirmed until the published v0.0.55 Debian package is deployed and genuinely new sequential and synchronized local searches return results within the operator budget without changing the index total before the crawler is started.
- A missing stored-document identity remains in Bleve until an explicit current-document lineage operation or full-index rebuild removes it. Search will continue to spend bounded candidate work filtering historical drift, but it will not turn that read into index persistence or merge work.
- One four-processor process is not validated for hundreds of complete HTTP requests with projection, evidence, peer work, and response encoding. Sustained hundreds-request service needs separately implemented and measured horizontal read capacity with independent CPU, I/O, immutable index generations, query-ready document projections, freshness-aware routing, queue-inclusive admission, and one-replica-loss capacity.
- Same-host processes sharing the current four processors are not additional capacity. Multiple processes must not open one live mutable Scorch directory. Immutable index-generation distribution and replica-aware routing are not part of this release.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class, and deployed releases show no recurrence of its corrupt-frequency OOM symptom. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
