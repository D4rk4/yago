## Abstract

YaGo v0.0.42 corrects a cold-search regression introduced in v0.0.41. Stored-candidate validation now reads only the requested result page in one document-vault snapshot; Bleve's fourfold overfetch tail stays lazy unless an orphan or post-filter requires another bounded page. This preserves the transaction reduction without multiplying cold random reads. No data migration, writer-generation change, dependency update, setting, wire shape, or deployment-topology change occurs. Operators running v0.0.41 can upgrade in place; rollback to v0.0.41 is data-compatible. Production confirmation remains required after published-package deployment.

## Changes

### Bound stored-candidate snapshot pages

The lexical ranking stage requests 50 local candidates. The disk backend deliberately asks Bleve for up to four times that number so missing documents and stored-document filters do not leave the visible page short. v0.0.41 passed all 200 overfetched hits to one ordered presence lookup before result collection. That reduced the number of document-vault transactions but made a healthy 50-result path touch the entire overfetch tail.

Production established the consequence. On v0.0.41, repeated common queries completed quickly after their document-location pages were resident, while fresh common queries such as `linux kernel`, `machine learning`, `network security`, and `cloud computing` exhausted the 1.8-second interactive budget. The node remained healthy and ready. Source tracing showed that the affected path performed presence work for 200 candidates before the result loop could stop at 50.

Stored-candidate presence is now prepared in requested-result-size pages. The first visible page uses one ordered document snapshot for at most 50 identities in the ordinary ranking path. Bleve hits beyond that page remain untouched when all requested candidates are present. A missing, malformed, or filtered candidate lets the result loop continue and opens another bounded page only when it reaches that page. Facet and post-filter searches retain honest complete scanning through successive bounded pages.

Position alignment, duplicate identity handling, orphan reporting, Bleve totals, stored projection decoding, and lazy full-document fallback are unchanged. Implementations without ordered set presence continue to use the established individual compatibility path. No cache identity, ranking coefficient, search deadline, result shape, or crawler behavior changes.

- Missing documents and projections that cannot answer the request still use the established orphan or full-document paths. Complete facet and post-filter requests still scan every bounded Bleve hit needed for honest totals.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.42 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.42`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Wait for exact v0.0.42 identity, health, readiness, stable restart count, and bounded logs. Exercise several previously unseen common queries before repeating them so the acceptance check covers both cold and warm paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm a new logical session, continued crawl and index progress, DDGS behavior under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.41, stop both services, install the exact published v0.0.41 package, and start the node before the crawler. The stored and derived-index formats are identical, so no rebuild is expected. The v0.0.41 cold-query regression returns with that rollback. Rollback to v0.0.38 retains the v0.0.41 generation boundary and therefore follows the complete derived-index rebuild procedure documented by that release.

## Known limitations

- Production success remains unconfirmed until the published v0.0.42 Debian package is deployed and multiple genuinely cold common queries complete within the fixed interactive budget before the crawler is started.
- A requested candidate page still performs document-location and ordered-document presence reads for its identities, followed by stored evidence for the leading results. The correction removes accidental overfetch work; it does not make those required reads free or change the fixed search deadline.
- Published v0.0.41 remains immutable. Its node starts and serves correctly, but its eager overfetch validation can still make cold common queries incomplete.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class. They do not add a general decoder allocation bound for arbitrary current-generation corruption; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
