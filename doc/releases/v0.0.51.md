## Abstract

YaGo v0.0.51 reranks complete lexical candidates inside the same Bleve reader snapshot that enumerated them. Ordinary analyzer-scoped search now performs one native alias request: each child supplies a complete zero-score internal-identity filter or retains exhaustive scoring on overflow. This removes the remaining external-identity materialization and resolution work that caused cold v0.0.50 production requests to exceed their deadline. Exact production-copy results and all current-source closure gates pass. Stored data, APIs, settings, wire behavior, and deployment topology are unchanged; rollback to v0.0.50 requires no rebuild. One four-CPU process is still not a 200-request read tier.

## Changes

### Keep candidate identities inside one reader snapshot

Release v0.0.50 first collected external document identities, then opened another Bleve reader snapshot to rerank the complete candidate set. Shard ownership prevented every child from resolving every identity, but each owning child still had to translate its external identities back to segment-local document numbers through its finite-state indexes. A cold production request could continue spending CPU after its HTTP deadline even when its candidate set was small.

Ordinary analyzer-scoped disk search now constructs one conjunction containing the unchanged scoped query and a private lexical-candidate query, then submits that conjunction once to the native Bleve alias. Bleve opens each child reader and constructs both searchers against that reader. The private query enumerates the existing positive lexical union without scoring and copies each segment-local identity before Bleve reuses its match object.

When a child exhausts at 4,096 candidates or fewer, their copied internal identities are sorted and exposed as a zero-score filter in that same reader. A complete empty set matches nothing. A 4,097th candidate selects a zero-score MatchAll filter, so the unchanged scoped query remains exhaustive for that child. Skew therefore enlarges work instead of truncating recall. Cancellation, a missing identity, or construction, iteration, count, reader, or close failure remains an operational failure.

The native alias remains authoritative for child concurrency, BM25 scoring, result merge, equal-score order, pagination, status, errors, cancellation, and field scores. Explicit diagnostic explanations retain the exhaustive query and its established explanation tree. No segment-local identity crosses an `IndexReader`, cache, or request boundary.

This change deletes the v0.0.50 transparent child wrappers, request-context shard positions, external-identity grouping, and compatibility fallback. Exact analyzer-token coalescing remains active. There is still one bounded path rather than parallel implementations with overlapping ownership.

### Preserve exact fallback and horizontal capacity boundaries

The per-child 4,096 limit conservatively partitions the established 32,768-candidate alias limit across eight children. One skewed child can fall back to exhaustive scoring even when the alias-wide total would have fit. It can never return a partial candidate set as complete.

Across thirteen terms on a read-only production-index copy, the same-snapshot path retained exact final identities, order, scores, totals, and status. After normal startup cache and mapping preparation, a freshly reopened `seismology` query improved from 54.03 milliseconds to 6.43 milliseconds with the same 51 returned hits and total of 113.

On four processors, 200 mixed same-snapshot requests completed in 3.331 seconds with one admitted alias request and in 2.757 to 2.957 seconds with wider admission. Using the slower stable boundary and the ordinary 600-millisecond exact-stage budget gives `3.331 / 0.600 = 5.55` four-CPU capacity units. Six active read replicas are therefore the initial validation target, and N+1 starts at seven.

That arithmetic is not a production guarantee. Representative cold HTTP service time, balanced routing, independently current index state, and one-replica-loss behavior still require measurement. This release does not add replicas or routing. That runtime is a new service boundary requiring a separate accepted ADR and synchronized state, health, Docker, systemd, Debian package, rollout, and rollback design.

ADR-0072 records the same-reader identity lifetime, completeness, failure, and capacity rules and amends ADR-0070 and ADR-0071. The release audit matched all 73 numbered ADR files to 73 unique index entries. Sixty-nine decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision proposal template. The previously delayed ADR-0063 remains implemented, and ADR-0072 maps to the runtime, exact-result, refusing, unchanged-input, failure, and race evidence. No accepted or queued ADR implementation remains knowingly outstanding.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.51 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.51`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.51 identity, health, readiness, indexed document total, stable restart count, and bounded logs. Exercise several genuinely new local queries and a bounded concurrent probe before repeating them so acceptance covers first-use, warm, and contended paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm its connected state, a new logical session, manual and web-ingest crawl-order progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.50, stop both services, install the exact published v0.0.50 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores the measured external-identity resolution and can expose the same cold-search deadline failure.

## Known limitations

- Production success remains unconfirmed until the published v0.0.51 Debian package is deployed and several genuinely new queries plus a bounded concurrent probe complete within the operator budget before the crawler is started.
- A single four-CPU process is not validated for a synchronized 200-request burst inside the ordinary exact-stage budget. Six active replicas and seven for N+1 are initial capacity targets derived from isolated-copy work, not a deployed guarantee. The replicated-read runtime is not part of this release.
- A child with more than 4,096 positive lexical candidates retains exhaustive BM25 retrieval. Exact bounded scoring for broad or highly skewed terms requires persisted block score upper bounds or another separately accepted backend; the current zapx format does not provide them.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class, and deployed releases show no recurrence of its corrupt-frequency OOM symptom. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
