## Abstract

YaGo v0.0.36 prevents a confirmed Bleve segment-writer defect from turning a merge into an unbounded allocation. Production v0.0.35 used zapx v17.1.2, which encoded incorrect posting offsets when an intermediate chunk was empty; a later merge decoded an impossible frequency and requested 406 GB. This release uses corrected v17.1.4, rebuilds or refuses pre-fix indexes before opening Scorch, bounds merge input and segment size, and validates the node lifecycle under an exact 4 GiB limit. Admin Network now explains crawl-gated DHT distribution. Builds use security-patched Go 1.26.6. Existing indexes rebuild once before listeners open; no protocol, setting, port, or service-topology change is introduced.

## Changes

### Correct the zapx empty-chunk writer defect

The production v0.0.35 node exited from the Go runtime with an out-of-memory failure while Bleve merged Scorch segments. The decoder read a posting frequency of 3,172,724,355 and attempted to allocate a 406,108,717,440-byte location slice. Systemd recorded a 23.5 GiB process peak; the kernel and service cgroup recorded no OOM kill or memory-limit event.

Read-only inspection found the impossible frequency in a CRC-valid source segment, under the high-frequency URL term `www`, after document drops had produced an empty posting chunk between two nonempty chunks. zapx v17.1.2 converted chunk lengths `[1,0,1]` to offsets `[1,2,3]` over a two-byte payload. Upstream commit `388c73a` corrected the in-place conversion, and zapx v17.1.4 is the first released version that returns `[1,1,2]`. The node now selects v17.1.4. Its required Bleve index API and transitive vector-library versions move with that module selection.

These measurements are from the separately operated `yagoseek.dev` production node. They do not establish the cause of issue #3 on the reporter's system. That reporter later identified v0.0.35 and approximately 172 MiB for the node plus 60 MiB for the crawler; no pressure or OOM evidence was reported there.

### Rebuild pre-fix indexes before Scorch can decode them

The derived disk index now has an external writer-generation file, `search.bleve.segment-generation`. A new index records the corrected generation. Before Scorch opens an existing root or shard, an absent or stale generation persists the existing rebuild-required marker. When authoritative stored documents are available, the node replaces the derived index from that source. When no rebuild source exists, it refuses the old index instead of exposing the decoder to a segment written by v17.1.2.

A successful rebuild writes the generation file with mode 0600 before clearing the rebuild marker. Tests cover new, current, stale, missing, unreadable, unwritable, and symlinked paths; marker persistence and preservation; rebuild-source presence and absence; and both accepting and refusing directions. The former legacy single-shard open path was removed because generation admission makes it unreachable.

### Bound Scorch merge work and prove the node under 4 GiB

Each Scorch shard now uses one persister worker, accepts at most 32 MiB of in-memory segment input per worker, and limits a merged segment to 100,000 documents instead of 400,000. These limits reduce simultaneous merge residency and make large indexes progress through smaller replaceable units.

Both Docker interaction suites now create every node container with exactly 4 GiB of memory and the same memory-plus-swap value, then inspect the effective Docker host configuration before use. The node suite exercises index work, backup and restore, and real YaCy exchange. The crawler suite keeps the crawler running while restarting only the node, then keeps the node running while restarting only the crawler; both replacements establish new logical sessions and crawl work continues. DDGS result materialization also completes under that node limit.

### Explain the active-crawl DHT gate

The DHT distribution gate correctly closes while a crawl is active unless the operator enables distribution during crawling. Automatic web-discovery and `swarm-seed` profiles are active crawls even when a custom profile was cancelled. Admin Network now recognizes only the exact closed `crawl_idle` gate with reason `crawl is in progress`, explains those active profiles, and offers two procedures: wait until the crawl queue is empty, or open Configuration → Swarm, enable **Distribute while crawling**, save, and restart the node. Other closed or unobservable gates receive no inapplicable advice.

### Use the patched Go 1.26.6 baseline

Go 1.26.6, released 2026-08-13, contains security corrections in the Go command and the `crypto/tls`, `encoding/asn1`, `encoding/xml`, `html/template`, `net`, `net/http`, and `net/url` standard-library packages. Every module and the workspace require that exact patch release. Both Docker build stages pin the Docker Official Image multi-architecture digest for Go 1.26.6. Application dependencies and runtime service topology are otherwise unchanged.

- zapx v17 moves from v17.1.2 to v17.1.4. `bleve_index_api` moves from v1.3.11 to v1.3.12 and the transitive `go-faiss` selection follows the corrected zapx module graph. Bleve remains v2.6.0 and no native runtime dependency is added.
- Source and CI builds now require Go 1.26.6 rather than an unspecified 1.26 patch. Released binaries remain self-contained and require no Go installation on the target.
- The existing Admin Overview memory diagnostics remain node-process measurements. They do not include the crawler, browser children, service cgroup, host page cache, swap, pressure events, or OOM events.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.36 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.36`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. An index created by v0.0.35 or earlier has no corrected-generation file, so expect one complete Bleve rebuild before any listener opens. Observe bounded logs, memory, the rebuild marker, and disk space; do not start the crawler until health and readiness succeed and the node reports v0.0.36.
5. Start `yago-crawler`, confirm v0.0.36 and a new accepted logical session, then observe fetches, accepted ingest batches, index growth, search responses, service restart counts, memory diagnostics, cgroup events, and bounded logs across repeated intervals.

For rollback, stop crawler and node. Before intentionally starting v0.0.35 or earlier, remove only `/opt/yago/data/search.bleve.segment-generation`; the old writer ignores that file and may add v17.1.2 segments, so retaining the corrected-generation claim would let a later v0.0.36 upgrade trust mixed-writer output. Reinstall the older package, start and verify the node, and then start the crawler. A later re-upgrade will rebuild the derived index again. No data restore is required solely for protocol or stored-document compatibility, but rollback reintroduces the known writer defect and broader merge bounds.

## Known limitations

- Upgrade from v0.0.35 or earlier performs one full derived-index rebuild before listeners open. Its duration depends on the stored document count and storage throughput; a proxy may return 502 during that planned interval unless the operator provides a maintenance response.
- The exact 4 GiB Docker gate proves the complete node/crawler interaction lifecycle on the bounded test corpus. It does not claim that the test corpus equals the much larger `yagoseek.dev` vault or that node, crawler, browser children, and host facilities together fit inside one 4 GiB cgroup. Production validation remains required.
- The generation guard prevents Scorch from opening indexes that may contain output from the confirmed v17.1.2 writer. zapx still has no general allocation bound for an arbitrary impossible posting frequency in a current-generation segment. That defense request and the production reproducer are tracked upstream in `blevesearch/bleve#2393`.
- File-backed bbolt and Bleve mappings can make process RSS large while anonymous memory and cgroup pressure remain low. This release bounds merge work and removes the confirmed 406 GB corrupt allocation; it does not make RSS alone a pressure or leak signal. Admin Overview, cgroup events, and host available memory must be interpreted together.
- Enabling **Distribute while crawling** still requires a node restart. This release explains that consequence at the closed gate but does not make the setting live-applied.
