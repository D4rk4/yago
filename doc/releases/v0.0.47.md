## Abstract

YaGo v0.0.47 carries the active-search-root cache loading from unpublished v0.0.46 and makes release image publication recover from an explicit transient registry blob refusal. Before readiness, the node sequentially reads referenced Scorch roots into reclaimable operating-system cache, then performs lexical warm-up. The tag workflow repeats the identical authenticated child push after two and four seconds only for an unavailable-blob response; every other error fails immediately, and the existing pull verifies exact image identity. APIs, stored formats, settings, and deployment topology are unchanged. One four-CPU replica still cannot guarantee hundreds of broad simultaneous searches; that requirement needs independently measured horizontal read capacity.

## Changes

### Load active persisted search roots before serving

Release v0.0.45 reduced the production index to one active root per Scorch shard, but consolidation did not populate arbitrary postings and stored-data pages. Five first-use queries still failed at the fixed local-search deadline. The initial burst incurred 387 major faults and about 42 MiB of physical reads; the four admitted Bleve searches remained occupied after their HTTP callers returned, and subsequent local searches were refused for exhausted capacity.

After any rebuild and bounded segment consolidation, the disk index obtains one referenced Scorch snapshot at a time and enumerates only that snapshot's nonempty persisted segment paths. It reads each active file sequentially to end through one reusable 4 MiB window, with one snapshot and one file open at a time. Holding the snapshot prevents retirement of an active file during the read. Retained inactive snapshots and in-memory segments are not read.

The loader checks cancellation before every shard and file and between windows. Snapshot acquisition, path opening, read, file close, snapshot close, invalid reader output, or no-progress output refuses index construction. Joined cleanup failures remain visible. Files are opened by basename inside their exact index directories. The operation does not write segment bytes, change file metadata, advance the writer generation, or alter mappings.

The existing lexical warm-up runs only after every active root has been read. Listeners and readiness remain closed until both stages finish, moving predictable sequential storage work ahead of interactive admission.

### Restart only an identical child push after a blob refusal

The v0.0.46 workflow had already validated both product images natively on amd64 and arm64 and exported their exact archives. During promotion, both amd64 children reached GHCR, but the arm64 node child push failed because the registry reported an unavailable blob. The workflow correctly created neither final manifest list nor release.

Each missing architecture child now normally performs one authenticated `docker push`. If and only if its output reports `unknown blob` or `blob unknown to registry`, the same content-addressed reference is pushed again after two seconds and, if necessary, after four seconds. A third refusal fails publication. Authorization, network, identity, and every other registry error fail after the first attempt.

Successful command exit does not establish acceptance. The existing publication path still pulls the exact architecture reference and matches its local image identity, architecture, source label, revision label, and manifest digest to the previously validated archive before composing a final manifest list. The retry changes transport timing only; it cannot rebuild, substitute, or silently accept a different image.

### Preserve an honest read-capacity model

Loaded segment pages are reclaimable operating-system file cache, not pinned application memory. A latency-sensitive node must budget the active roots together with heap, document-vault working set, and operating-system headroom. Startup duration is proportional to active-root bytes and storage throughput, and later memory pressure can reclaim the pages.

The production-sized synthetic gate exercised 100 and 200 distinct simultaneous queries at four and eight CPUs. Cache loading reduced first-round page faults, but CPU and scoring work still exceeded the response budget for many requests. The result rejects a wider queue or higher in-process concurrency as a general capacity solution. Deployments requiring hundreds of broad simultaneous searches must provision enough independently measured read replicas, or adopt a separately accepted bounded-retrieval backend, so each replica remains below its measured cold CPU and cache limit. This release preserves narrow search and document-store boundaries but introduces no runtime service boundary.

ADR-0068 records the cache-loading decision and capacity boundary. ADR-0051 now records the bounded registry transport retry without weakening immutable image identity. The release audit matched all 69 numbered ADR files to their index entries: 65 live decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are explicitly Superseded, and ADR-0000 is the non-decision proposal template. The previously delayed ADR-0063 remains implemented by conservative pre-serving filters and bounded post-open maintenance. No accepted or queued ADR implementation remains knowingly outstanding.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.47 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.47`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Allow the complete active-root read and lexical warm-up to finish before listeners and readiness appear. Verify exact v0.0.47 identity, health, readiness, indexed document total, stable restart count, cache-loader totals, and bounded logs. Exercise several never-before-used common local queries before repeating them so acceptance covers both first-use and warm paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm a new logical session, continued crawl and index progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.45, stop both services, install the exact published v0.0.45 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores readiness without the complete active-root read and can expose the same first-use physical faults. Rollback to v0.0.38 retains the generation-v2 boundary and follows the complete derived-index rebuild procedure documented by v0.0.41.

## Known limitations

- Production success remains unconfirmed until the published v0.0.47 Debian package is deployed, active-root loading completes, and multiple genuinely new common local queries complete within the fixed interactive budget before the crawler is started.
- Cache residency is reclaimable. A target whose active roots plus required heap, vault working set, and operating-system headroom do not fit available memory cannot claim the same first-use latency after reclaim.
- First readiness is delayed in proportion to active persisted bytes and storage throughput on every start. The loader intentionally fails closed; it has no skip setting because exposing a predictably cold index would recreate the incident.
- Synthetic burst results explicitly disprove a universal single-replica hundreds-request guarantee. Horizontal read capacity or a separately accepted bounded-retrieval service remains a future topology change with its own ADR and synchronized Docker, systemd, and package work.
- The child-push retry recognizes only the explicit unavailable-blob class. Persistent registry refusal, authorization failure, network failure, or any ambiguous error still stops publication; it never weakens image or provenance verification.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class. They do not add an independent decoder allocation bound for arbitrary corrupt frequency data; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
