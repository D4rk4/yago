## Abstract

YaGo v0.0.27 stops the peer roster from taxing every storage write. Each write yields to active interactive reads before admission, so a needless read slows every writer; the roster recomputed a Prometheus gauge with an all-shard read transaction on every observation, though the gauge is scraped once a minute. On the reference deployment the node held 191 percent CPU while the crawler sat at 10 percent and crawled at half a page per second. The count is now sampled at most once every five seconds, a failed count no longer reports zero, and a stored posting writes its referenced-URL row once per URL instead of once per word. Read priority is unchanged.

## Changes

### The peer roster stops recomputing a gauge with an all-shard read

- Every storage write yields to active interactive reads before it is admitted, for up to fifty milliseconds. That is deliberate read priority, and it stays. Its cost is that each foreground read slows every concurrent writer, so a read taken more often than its result is consumed is pure loss.
- The roster took exactly such a read. Observing a peer recomputed the known-peer gauge through a read transaction opened on every shard, and the only consumer is a Prometheus gauge scraped every fifteen to sixty seconds. The count is now sampled at most once every five seconds. The reachable-peer gauge is computed in memory and still updates on every observation.
- The count runs outside the sampler's lock. The roster is observed synchronously inside the peer hello handler under a one-second budget, and a mutex cannot honour a caller's deadline; a caller that blocked on one would outlive its own budget. Claiming the sampling interval under the lock still leaves at most one reader counting, so a slow read is not joined by a herd of identical ones.
- A failed count no longer overwrites the gauge with zero. The count fails when the read gives up under write pressure, which is exactly when an operator consults it, and reporting zero made the metric deny the roster at that moment. The last good sample stands instead.
- Overflow trimming marks its two reads as background work. That only skips the in-flight-read accounting that writers yield to; the deadline and cancellation of the caller propagate unchanged, and the interactive admin count stays foreground.

### A stored posting writes its referenced URL once, not once per word

- Recording a stored posting wrote the referenced-URL row for every posting, keyed on the URL alone. A document with three hundred distinct words issued three hundred writes of the same key, with an empty value, inside the transaction that holds all eight shard locks longest. The row is now written only when absent, matching the shape the sibling purge path already used.

## Compatibility

- No environment variable, Admin setting, route, request field, response field, status code, public schema, listener, port, service, image name, package path, Bleve mapping, document encoding, or deployment topology changes. No dependency changes. No contract or wire-format change.
- Read priority is unchanged. This release removes needless reads and writes so the yield fires less often; it does not shorten the yield, which would trade search latency for crawl throughput.
- `yacy_peer_known_total` is now up to five seconds stale, and after a failed sample the previous value stands for up to another interval. It no longer reports zero on a failed count. `yacy_peer_active_total` is unchanged and still exact.
- Stored data is untouched. The referenced-URL rows a previous release wrote remain valid; the change removes redundant rewrites of rows that already exist.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.27 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.27`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first, then `yago-crawler` after node readiness. Verify both versions, `/health`, `/ready`, and the configured listeners.
5. Watch the crawler's fetch rate and the node's CPU share. The node should shed CPU and the crawl rate should rise; search latency should not move, because the read yield is unchanged.
6. Keep production verification observation-only.

For rollback, stop crawler and node, reinstall the v0.0.26 package, start and verify the node, and then start the crawler. No index rebuild or data restore is required. The older node resumes recomputing the gauge on every observation and resumes rewriting the referenced-URL row once per word.

## Verification

- The complete Go 1.26 `make verify` gate passed: tidy, formatting, vet, pinned lint, architecture checks, every module race suite with zero data races, all builds, and exact statement coverage.
- Both changesets were reviewed adversarially against the working tree. The review found that the sampler held its lock across the storage read on the synchronous hello path, which a mutex cannot reconcile with a caller's deadline; that is corrected here, and the corrected form was exercised under the race detector.
- Every guard ships with the test that proves it refuses and the test that proves it does not over-refuse: sampling within the interval takes one count while the reachable gauge still updates, advancing the clock past the interval forces a fresh count, a failed count leaves the previous value standing, the interactive count stays foreground, a cancelled parent still stops the background read, two URLs still get their own rows, and a purged URL is recorded again.
- Every test was proved meaningful by removing or inverting the guard it pins and recording the resulting failure.

## Known limitations

- The remaining contributors to write-gate saturation are not addressed. The RWI intake transaction is still unbounded in size and can hold all eight shard locks through thousands of operations; the peer-reputation writer still scans every peer inside its write transaction; the transfer tally still takes a writer's mutex on its read path; and overflow trimming still runs on the synchronous hello path, where a saturated roster scans its whole reservoir.
- The effect on production throughput is predicted, not yet measured. The prediction is that the node sheds CPU and the crawl rate rises while search latency holds; the release notes the measurement to take rather than claiming the outcome.
- `observedPeerRoster` remains constructible without its sampler. Only the constructor installs one, and a literal that omits it would fault on the first observation.
- The known-peer gauge trades freshness for the read it no longer takes. An operator watching a roster change during those five seconds sees the previous value.
