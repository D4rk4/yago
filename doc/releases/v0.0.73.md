## Abstract

Yago v0.0.73 reduces node write work during crawl ingest. Ingest no longer rewrites and re-indexes a stored link target once for every source page that links to it. It stores the target's anchor contributions and a small durable refresh mark instead. A background node pass every ten seconds refreshes each marked target once, so anchor text reaches search after that pass. One storage update now commits its changed shards concurrently instead of in sequence. The node adds one internal storage collection. Rolling back to v0.0.72 keeps the collection but ignores it. No setting, environment variable, listener, message shape or dependency changes. Node and crawler may be upgraded in either order.

## Changes

### Deferred, coalesced inbound-anchor target refresh

When a crawled page is stored, the node replaces the inbound anchors that page contributes to each of its link targets. Before this release, every stored target document was rewritten and offered to the search index again in the same step, once per source page. A target linked from many pages was rewritten and re-indexed once for each of them. On a production node this target stage took more than half of ingest time.

Ingest now stores the target's anchor row. When the target is stored and its effective inbound anchors change, ingest also writes a refresh mark that names the replaced source pages. Marks for one target merge. A mark that would name more than 256 sources covers all sources instead. Ingest does not rewrite or re-index the target document.

A node background pass runs every ten seconds and refreshes marked targets in pages of at most 64 until no mark remains. Each page holds the targets' write locks. It recomputes their inbound anchors from the anchor rows and offers the changed documents to the search index. It then stores those documents and removes their marks, within the existing transaction row and byte limits. A target that is missing or whose anchors did not change loses its mark without a write. An index or storage failure keeps the mark for the next pass, and marks survive a restart. Document revision reads apply a pending mark, so later ingest and lineage decisions see current anchors.

Search may show a target's previous anchor text until the next pass completes. Anchor text is a ranking signal, so this delay does not remove documents from results.

### Concurrent shard commits

One sharded-vault update now commits its changed shards concurrently instead of one after another, so it waits for about the slowest shard flush rather than the sum. Shards that did not change are still rolled back without a commit. When several commits fail, the lowest-numbered shard failure is reported. Each shard is still committed independently, as before.

### README

The root README is a short project landing page with links to the existing guides. No runtime change.

## Compatibility

- No YaCy, Tavily or node-crawler message shape or status code changes.
- Node and crawler from this release interoperate with the v0.0.72 node and crawler; they may be upgraded in either order.
- The node adds the storage collection `document_inbound_anchor_refreshes`. Existing data needs no conversion; stored documents keep their current inbound anchors until a source page changes them.
- No setting, environment variable, listener, service, image repository or new dependency is added. The refresh interval and page size are fixed.
- The reusable-module API gate compares against the exact previous published v0.0.72 tag and source commit.

## Upgrade and rollback

Verify the published package's GitHub-hosted attestation against repository `D4rk4/yago`, the exact release workflow, tag ref and source commit. Use matching node and crawler binaries. Preserve configuration and data; ordinary deployments should use the established stopped-service backup procedure. Where an explicit target-specific operator policy omits a new pre-upgrade backup, preserve every existing archive unchanged.

Stop the crawler and node, install the published package, then start and verify the node before starting the crawler. The package enables the units but does not start them automatically.

Rollback reinstalls the previous verified matching package with both services stopped. v0.0.72 ignores the refresh collection. Targets with a pending mark at rollback keep their previous anchor text in search until a later source page change rewrites them.

## Known limitations

- Anchor text from a newly crawled source reaches search only after the next background pass. A large backlog of marks drains in pages of 64 targets per pass step.
- Devices with a single command queue may see a smaller gain from concurrent shard commits.
- Bug #3 (node memory use) remains open; this release does not change memory behavior.
