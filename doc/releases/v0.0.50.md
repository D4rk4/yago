## Abstract

YaGo v0.0.50 removes redundant cross-shard identity resolution from complete lexical candidate reranking. Each Bleve child now resolves only candidates it produced, while the existing alias remains authoritative for scoring, merge, ordering, status, and failures. Exact analyzer-token duplicates also share one candidate clause without language guessing. Ambiguous ownership retains the established complete fallback. On a read-only production-index copy, 200-request four-CPU bursts improved 2.40 to 2.96 times with exact result equality. Stored data, APIs, settings, and deployment topology are unchanged; rollback to v0.0.49 requires no rebuild. One replica still does not satisfy hundreds of simultaneous bounded-latency reads.

## Changes

### Resolve complete candidates only on their owning shards

Release v0.0.49 collected a complete bounded lexical candidate set before exact analyzer-scoped BM25 reranking. Its zero-boost document-identity restriction supplied the complete candidate list to the eight-child Bleve alias. Every child therefore resolved every candidate identity, including identities produced by the other seven children, and supplied that list to each active segment.

A CPU profile of 200 searches over a read-only copy of the production index attributed about 69 percent of cumulative CPU time to Scorch and zapx document-number resolution, principally vellum finite-state-transducer lookup. The established alias-wide identity path consumed 40.36 CPU-seconds during one 10.39-second wall-clock round on four processors.

Candidate hits already identify the Bleve child that produced them. The disk read alias now wraps each child transparently with its stable position. When every configured child name is nonempty and unique and every candidate names a configured child, a private zero-boost identity query supplies each child only the identities it produced. The same single Bleve alias remains authoritative for child concurrency, BM25 scoring, merge, equal-score order, pagination, status, errors, cancellation, and field scores.

Missing, nil, empty, duplicate, or unknown ownership cannot narrow the result. Those cases retain Bleve's established alias-wide document-identity query with the complete flattened set. A plain alias without the private child position also receives the complete set.

Nine measured query shapes retained the exact candidate identities and exact final identities, order, scores, totals, status, and field scores. Two native-alias 200-request rounds completed in 4.330 and 3.808 seconds, with p99 of 4.326 and 3.781 seconds. Comparable alias-wide rounds completed in 10.393 and 11.279 seconds, with p99 of 10.183 and 11.161 seconds. The corrected path is 2.40 to 2.96 times faster for this measured burst.

### Coalesce exact analyzer token streams

The positive candidate union previously repeated clauses when several analyzers emitted the same exact token stream for one source term. Bleve constructs each candidate MatchQuery from that analyzed stream. With the same fields, boosts, fuzziness, prefix, and unscored union, equal streams address the same postings and provide no additional recall.

The candidate builder now retains the first analyzer for each exact per-term token stream. It retains an analyzer when its stream cannot be obtained and retains every Chinese or Japanese dictionary branch independently. It does not infer a language and does not use script guesses, semantic word lists, or localized synonym rules. On the nine production-copy terms, the candidate analyzer count fell from 17 to between two and five while preserving the complete token evidence and final search result.

### Preserve an explicit horizontal read-capacity boundary

This correction reduces work within one replica; it does not turn one four-CPU process into a 200-request deployment. Using the slower corrected round and the ordinary 600-millisecond exact-stage budget gives `4.330 / 0.600 = 7.22` equally loaded four-CPU capacity units. Eight active read replicas are therefore the initial validation target for 200 synchronized requests, and N+1 starts at nine.

That arithmetic is not a production guarantee. The complete cold HTTP path, production query mix, independent local index state, balanced routing, replica freshness, and one-replica-loss behavior still require measurement. This release does not introduce the replicated-read runtime. That is a new service boundary requiring a separate ADR and synchronized state replication, routing, health, Docker, systemd, Debian package, rollout, and rollback design.

ADR-0071 records the shard-owned candidate and capacity rules and amends ADR-0070. The release audit matched all 72 numbered ADR files to 72 unique index entries. Sixty-eight live decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision proposal template. The previously delayed ADR-0063 remains implemented, and ADR-0071 is implemented by the candidate ownership, analyzer equivalence, conservative fallback, alias behavior, and bidirectional test paths. No accepted or queued ADR implementation remains knowingly outstanding.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.50 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.50`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.50 identity, health, readiness, indexed document total, stable restart count, and bounded logs. Exercise several genuinely new local queries and a bounded concurrent probe before repeating them so acceptance covers first-use, warm, and contended paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm its connected state, a new logical session, manual and web-ingest crawl-order progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.49, stop both services, install the exact published v0.0.49 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores the measured redundant identity and analyzer work and can expose the same cold-search deadline failure.

## Known limitations

- Production success remains unconfirmed until the published v0.0.50 Debian package is deployed and several genuinely new queries plus a bounded concurrent probe complete within the operator budget before the crawler is started.
- A single four-CPU process still cannot satisfy a synchronized 200-request burst inside the ordinary exact-stage budget. Eight active replicas and nine for N+1 are initial capacity targets derived from isolated-copy work, not a deployed guarantee. The replicated-read runtime is not part of this release.
- Candidate sets above 32,768 documents retain exhaustive BM25 retrieval. Exact bounded scoring for those broad queries requires persisted block score upper bounds or another separately accepted backend; the current zapx format does not provide them.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class and deployed releases show no recurrence of that corrupt-frequency OOM. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
