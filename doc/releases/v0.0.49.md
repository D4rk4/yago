## Abstract

YaGo v0.0.49 bounds the avoidable analyzer-scope work observed in production search. Eligible disk searches first collect a complete, bounded lexical candidate set and then apply the unchanged analyzer-scoped Bleve query to that entire set. Incomplete or over-limit candidate sets retain exhaustive retrieval, so the optimization never silently truncates results. Per-process disk-read admission prevents competing eight-shard searches from amplifying CPU contention. Stored data, APIs, settings, and deployment topology are unchanged, and rollback to v0.0.48 requires no rebuild. One four-CPU node still cannot guarantee a 200-request burst; deployments requiring hundreds of simultaneous bounded-latency reads must provision and validate horizontal read capacity.

## Changes

### Bound analyzer-scoped retrieval with complete lexical candidates

Production v0.0.48 populated every active Scorch mapping before readiness, but eight new local terms still exceeded the 1.8-second interactive budget. Each request consumed about 2.44 to 2.74 CPU-seconds before returning an explicit incomplete result. An immediate repeat completed in 59 milliseconds with local results. A read-only copy of the exact 559,099-document production index showed that about 491,699 zero-boost analyzer-scope postings participated in each failed query, while the corresponding positive content requirements covered 158 to 34,824 postings.

For an analyzer-scoped ordinary disk search, the node now constructs an unscored disjunction from every distinct positive lexical requirement across the same text, URL, language, dictionary, and fuzzy analyzers. It omits analyzer scope, exclusions, domain constraints, and optional expansion terms from this first stage. Their omission can only enlarge the candidate set, so every full-query match remains in the candidate superset.

The candidate request asks for 32,769 documents. If it exhausts with at most 32,768 unique identities and reports no unseen tail, the node intersects the unchanged analyzer-scoped query with a zero-boost identity restriction over the complete set. Bleve remains authoritative for final matching, BM25 scoring, ordering, field scores, and totals. A complete empty candidate set remains an honest empty answer.

The 32,769th sentinel, a total larger than the returned set, an incomplete shard, cancellation, or an operational error cannot produce a truncated success. An over-limit candidate set uses the established exhaustive query unchanged. Explicit diagnostic explanation requests also retain exhaustive retrieval because an identity restriction would change Bleve's public explanation tree even when scores are equal.

On the isolated production copy, complete candidate sets contained 148 to 3,277 documents for eight failed terms and 29,871 for `economics`. Candidate collection took 1.7 to 23.3 milliseconds and exact reranking took 3.8 to 112.0 milliseconds on the warm copy. All nine queries retained the same 100 reference identities. These measurements establish the corpus relation and result equivalence; they are not a production latency guarantee.

### Admit disk reads within measured per-process capacity

The node admits `max(1, GOMAXPROCS / 8)` active disk-index reads per process, matching the fixed eight-shard Scorch fan-out. Waiting is bounded by the caller's existing context, and every success, failure, cancellation, and cancellation race releases admission exactly once. The existing outer search, fuzzy, remote, and HTTP admissions are unchanged.

This is overload protection rather than hidden throughput. On the read-only production copy with four processors, an unlimited mixed 200-request burst reached p99 10.851 seconds and every request exceeded the budget. With one admitted read, service time was p50 27.2 milliseconds, p95 240.4 milliseconds, and p99 258.9 milliseconds, but queue-inclusive p99 for all 200 requests remained 10.510 seconds. One process therefore cannot satisfy that burst.

A deployment requiring hundreds of simultaneous bounded-latency reads must provision enough independently measured read replicas that the queue on each replica remains within budget. The warm-copy measurements imply at least six four-CPU replicas by work divided by budget, with eight providing warm-copy headroom for a 200-request burst. Production storage and query-mix measurement remains authoritative. This release does not introduce a replicated-read service boundary; that requires a separate ADR and synchronized Docker, systemd, package, state-replication, health, and rollout work.

ADR-0070 records the bounded candidate and admission rules and amends ADR-0069. The release audit matched all 71 numbered ADR files to 71 unique index entries: 67 records are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision proposal template. The previously delayed ADR-0063 remains implemented, and ADR-0070 is implemented by the candidate, fallback, admission, and bidirectional test paths. No accepted or queued ADR implementation remains knowingly outstanding.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.49 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.49`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.49 identity, health, readiness, indexed document total, stable restart count, and bounded logs. Exercise several genuinely new local queries and a bounded concurrent probe before repeating them so acceptance covers first-use, warm, and contended paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm a new logical session, crawl-order creation and progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.48, stop both services, install the exact published v0.0.48 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores exhaustive analyzer-scoped retrieval and can expose the same first-use CPU and deadline failure.

## Known limitations

- Production success remains unconfirmed until the published v0.0.49 Debian package is deployed and multiple genuinely new queries plus a bounded concurrent probe complete within the operator budget before the crawler is started.
- Candidate sets above 32,768 documents retain exhaustive BM25 retrieval. Exact bounded scoring for those broad queries requires persisted block score upper bounds or another separately accepted backend; the current zapx format does not provide them.
- Per-process read admission prevents competing eight-shard scans from multiplying local work but does not add throughput. A single four-CPU process cannot satisfy a synchronized 200-request burst inside the 1.8-second budget. Horizontal read capacity remains an explicitly measured deployment requirement and is not introduced by this release.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class and deployed releases show no recurrence of that corrupt-frequency OOM. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
