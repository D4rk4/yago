## Abstract

YaGo v0.0.52 removes a process-wide search convoy found after v0.0.51 deployment. Disk search admission now covers only one native Bleve page call and releases before document presence, projection, filtering, evidence, and result mapping. Capacity is one native page per available Go processor; complete scans reacquire per page. On a read-only production-index copy, 200 synchronized candidate reads completed without error in 1.0924 seconds at four processors, but this is not an end-to-end SLO. APIs, formats, settings, and deployment topology are unchanged. Rollback to v0.0.51 requires no rebuild; production acceptance still precedes crawler restart.

## Changes

### Release native admission before projection

Release v0.0.51 admitted one complete disk-backed `SearchIndex.Search` call on the four-processor production node. One native alias query already fans across all eight Scorch shards, so the earlier capacity calculation divided processor count by shard count and produced a single slot. That slot remained held after Bleve returned, while the request checked document presence, decoded stored projections, applied filters, hydrated evidence, handled orphaned entries, and mapped final results.

Production exposed the resulting convoy. In one eight-request result-bearing burst, four callers exhausted outer capacity after approximately 315 milliseconds and four admitted callers reached the 1.8-second deadline. Across the complete burst the process consumed only 0.15 CPU-seconds, incurred one minor fault, no major fault, and no physical input. A repeated request completed in 125.6 milliseconds after the held operation returned. The failed burst was therefore blocked behind one whole-search token while processors and storage were effectively idle.

Disk read admission now encloses one `IndexAlias.SearchInContext` page call. The token is acquired immediately before the native call and released when that call returns. Document count, presence, projection, filtering, evidence hydration, orphan handling, and result mapping do not retain it. Complete filtered or faceted scans reacquire admission for each native page and release it before processing that page.

Tests prove both directions of the boundary. A blocked native page keeps the next native call out of Bleve, a canceled waiter enters no native work and retains no token, and release admits the next page. A separate test blocks projection after the first native result and proves that another native page can enter while projection remains blocked.

### Use available processors without widening request budgets

Native page capacity is `max(1, GOMAXPROCS)`. Go remains responsible for scheduling the shard goroutines on those processors. The existing public request limit, interactive pipeline admission, stage admission, deadlines, remote-provider admission, and failure classification are unchanged. The correction removes an inner head-of-line boundary; it does not lengthen a deadline or silently accept unbounded work.

On the disposable read-only production-index copy, four processors completed 200 synchronized candidate reads in 1.0924 seconds. Queue-inclusive p50 was 716.3 milliseconds, p95 was 1.0473 seconds, p99 was 1.0892 seconds, and the maximum was 1.0893 seconds, with no error. The former four-worker path took 2.879 seconds on the same copy. These measurements cover native candidate retrieval, not live document evidence or HTTP response construction, and are not presented as an end-to-end service guarantee.

Hundreds of concurrent complete requests remain a horizontal capacity requirement. A replica must own independent processors and independently safe index state. Multiple processes on the current four-processor production host do not add capacity, and Bleve Scorch does not support multiple processes sharing one mutable index while a writer is active. A replicated read runtime therefore requires a separate accepted ADR covering immutable generation publication, freshness, routing, health, N+1 capacity, deployment topology, rollout, and rollback.

ADR-0073 records the page-scoped admission boundary and amends ADR-0072. FTR-198 records the implemented capability; FTR-195 and FTR-197 identify the superseded admission measurements. The release audit matched all 74 numbered ADR files to 74 unique index targets. Seventy live records are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision template. The previously delayed ADR-0063 remains implemented by FTR-187 and its post-open word-filter maintenance. No accepted or queued ADR implementation remains knowingly outstanding.

- YaCy wire endpoints, Tavily-compatible endpoints, public response shapes, crawler contracts, document and vault formats, Bleve segment format and generation marker, package paths, image names, ports, listeners, services, and deployment topology are unchanged.
- No environment variable, Admin setting, default, navigation item, shelf row, Prometheus series, dependency, systemd unit, Compose control, or runtime service boundary changes.

- Upgrade from and rollback to v0.0.51 are format-compatible and require no document or search-index rebuild. Rollback restores the whole-search single-width admission and its measured concurrent convoy.
- DDGS provider policy remains admin-opt-in. This release does not enable fallback by default or change engines, request syntax, result admission, crawl seeding, or human-facing provenance.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.52 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.52`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.52 identity, health, readiness, indexed document total, stable restart count, bounded logs, and resource counters. Exercise genuinely new local queries, an eight-request result-bearing burst, and repeated controls before accepting search.
5. Start `yago-crawler` only after node search acceptance passes. Confirm its connected state and new logical session, then prove manual and web-ingest crawl-order progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.51, stop both services, install the exact published v0.0.51 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores the measured whole-search single-slot behavior on a four-processor node.

## Known limitations

- Production success remains unconfirmed until the published v0.0.52 Debian package is deployed and genuinely new local queries plus the eight-request concurrent probe complete within the operator budget before the crawler is started.
- The 200-request measurement covers candidate retrieval on a read-only production-index copy. One four-processor process is not validated for 200 complete HTTP requests with live projection, evidence, peer work, and response encoding. Sustained hundreds-request service needs separately implemented and measured horizontal read capacity.
- Same-host processes sharing the current four processors are not additional capacity. Multiple processes must not open one live mutable Scorch directory. Immutable index-generation distribution and replica-aware routing are not part of this release.
- A child with more than 4,096 positive lexical candidates retains exhaustive BM25 retrieval. Exact bounded scoring for broad or highly skewed terms requires persisted block score upper bounds or another separately accepted backend; the current zapx format does not provide them.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class, and deployed releases show no recurrence of its corrupt-frequency OOM symptom. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
