## Abstract

Yago v0.0.65 adds confirmed clearing of pending crawl orders to the Admin Crawler page. Operators can discard waiting node work while preserving leased orders, running crawls, indexed documents and schedules. The monitor distinguishes pending orders from each run's pending URLs, which remain controlled by the existing Cancel action. Clearing uses a fixed deletion boundary and bounded transactions, with explicit completed and partial results. The confirmation works without JavaScript. No stored-format migration, new setting or wire-protocol change is introduced. Upgrade with matching node and crawler binaries; rollback removes the new control but cannot restore orders an operator has already cleared.

## Changes

### Clear waiting node orders from the Crawler page

The crawl monitor provides **Clear pending orders** when its queue is available and contains waiting work. A separate confirmation page shows pending and leased order counts and requires the exact phrase `CLEAR PENDING ORDERS`. The form uses the existing authenticated Admin session and CSRF protection and submits natively, including with JavaScript disabled. Its confirmation field is outside the monitor's periodic refresh.

The result refreshes the Crawler page with the number of completed removals. Missing or incorrect confirmation, unavailable queue information and an empty precheck do not call the clear operation. A complete zero-removal result remains a success; a backend error with zero removals remains an error. Partial failures show completed removals without exposing backend error details. The node's warning includes only its stable event name, removed count and trusted server span.

### Preserve queue ownership during clearing

The node first reconciles pending automatic-discovery recovery intents and then captures one exclusive order-sequence boundary. Ordinary orders accepted during preparation can be included. Only orders still pending below the captured boundary are eligible; later arrivals and work already claimed by a crawler remain.

Deletion uses transactions of at most 256 orders. Each transaction removes the pending rows and their priority indexes together. Automatic-discovery identities are released only when they belong to the removed sequence; identities owned by leased or newer work remain. Indexed discovery identities can be generic keys rather than URL strings, and older rows without the reverse identity retain sequence-checked cleanup. Ordinary submission idempotency receipts remain in place, so retrying a previously accepted manual request with the same key does not recreate its removed order.

Counts advance only after a successful transaction. Replayed transaction callbacks cannot duplicate the count or carry a rolled-back cursor. Cancellation, malformed state and storage errors stop further deletion and retain the completed count for the operator. Reopening the queue does not recreate cleared work from stale recovery intents. A new automatic-discovery submission can be admitted normally after its earlier pending order was cleared.

### Explain the two queue controls

The monitor labels node work as **pending orders** and **leased orders**, and each run's waiting pages as **Pending URLs**. The existing per-run **Cancel** action removes that run's pending pages and waits for in-flight page processing to finish. Its scope is unchanged.

The new queue-management guide covers both procedures, disconnected workers, partial results, preserved indexed data, recurring schedules and automatic producers. Clearing waiting orders does not disable Greedy learning, Web-discovery crawling, recrawl schedules or API submissions. Restarting a service retains its durable queue.

## Compatibility

- No YaCy, Tavily or node-crawler message shape changes. The new GET/POST route is confined to the authenticated Admin surface at `/admin/crawl/queue/clear`.
- No database bucket, stored format, dependency, runtime setting, environment variable, listener, image repository or service topology is added. No index rebuild is required.
- Queue labels change in the Admin monitor. The checkpoint/restart E2E predicates now match the explicit pending-order and leased-order labels; their counts, timeouts and lifecycle assertions are retained.
- Leased work, active fetches, indexed documents, saved profiles, schedules and settings are preserved by order clearing. Per-run cancellation retains its existing meaning.
- The reusable-module API gate compares against the exact previous published v0.0.64 tag and source commit.

## Upgrade and rollback

Verify the published package's GitHub-hosted attestation against repository `D4rk4/yago`, the exact release workflow, tag ref and source commit. Use matching node and crawler binaries. Preserve configuration and data; ordinary deployments should use the established stopped-service backup procedure. Where an explicit target-specific operator policy omits a new pre-upgrade backup, preserve every existing archive unchanged.

Stop the crawler and node, install the published package, then start and verify the node before starting the crawler. The package enables the units but does not start them automatically. Installing this release does not clear any queue; clearing requires an authenticated operator action and explicit confirmation.

Rollback reinstalls the previous verified matching package with both services stopped. The older version can read the unchanged storage format, but it does not offer the new clear control. A package rollback does not reconstruct orders already removed by a successful clear. Use a new crawl submission when that work is wanted again.

## Known limitations

- Queue clearing is a finite operation, not a switch that prevents future work. Automatic producers and clients may refill the queue afterward.
- Clearing node orders does not cancel leased work or globally cancel all active runs. Use the existing Cancel action on each applicable run to discard its waiting URLs; disconnected workers apply their queued controls after reconnecting.
- An interrupted operation can leave completed batches removed. Refresh the monitor and use a new confirmed clear for the remaining eligible orders. A cancelled or finished run can remain in recent history.
- Open bug issue #3, concerning memory usage, remains deferred: its unchanged historical evidence does not establish a current reproducible defect requiring a separate memory-policy change in this candidate. No open issue carried the exact `enhancement` label at the reviewed release scope.
