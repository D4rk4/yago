## Abstract

Yago v0.0.54 stops abandoned disk term-reader work at request deadlines. Production v0.0.53 completed seven of eight cold exact searches, while one returned incomplete and consumed about 3.99 CPU-seconds afterward. A synchronous Bleve boundary now checks context around term-reader construction, posting enumeration, and optimization, closes resources returned after cancellation, and preserves query validation, errors, scores, and optional reader capabilities. A disposable production-index copy retained identical results; warmed bounded pages took 2.12–6.54 milliseconds. APIs, formats, settings, and topology are unchanged, so no rebuild is required. This bounds observed late work; it does not claim that one four-processor node can serve hundreds of simultaneous requests. Production acceptance still precedes crawler startup.

## Changes

### Stop disk posting work at its request deadline

Production acceptance of v0.0.53 improved cold local search but did not complete it. Seven of eight genuinely new local-only terms returned complete result-bearing answers in 0.328 to 1.214 seconds. `proteomics` returned an incomplete zero after 1.955 seconds with `local search deadline exceeded`, then the node consumed approximately 3.99 CPU-seconds during the next three seconds. A fresh `metabolomics` request limited to one result reproduced the incomplete answer and late CPU; both immediate repeats were fast and result-bearing.

Bleve v2.6.1 passes the caller context into each Scorch term reader but does not inspect it while opening per-segment dictionaries, postings, and iterators. The term reader's `Next` and `Advance` paths likewise enumerate postings without inspecting that context. Exact query construction can therefore continue after its response objective is lost, occupy native-page capacity, and delay later requests.

Every ordinary requested-hit and complete disk page now carries one deadline-aware query boundary. It preserves the original query's validation and composes with the v0.0.53 fuzzy-dictionary boundary. The boundary checks context immediately before and after term-reader construction, `Next`, `Advance`, and supported Scorch optimization. Cancellation before an operation performs no underlying work. Cancellation during an operation returns after that operation, closes a newly returned resource, and permits no later term-reader operation. Honest posting exhaustion and existing open, read, advance, optimization, and close failures retain their established meanings.

The wrapper exposes term-reader optimization, fuzzy automata, and BM25 cardinality only when the underlying reader supports each capability. It carries the deadline through Bleve's shared optimization context and wraps an optimized term reader returned by `Finish`. A reader canceled before a cardinality read reports zero without another underlying posting operation, allowing query construction to reach its context error. In-memory search is unchanged.

The boundary is synchronous. It adds no goroutine, detached cleanup path, cache, timer, lock, or admission channel. One Bleve operation that is already executing remains the hard interruption bound. The production-copy comparison ran raw and bounded production-shaped exact queries for four terms. Every total, ordered hit identity, BM25 score, and Bleve cost was identical. Warm bounded pages completed in 2.12 to 6.54 milliseconds. Only the disposable copy was opened by candidate code.

ADR-0075 records this boundary and amends ADR-0074 and ADR-0073. FTR-200 records the implemented capability; FTR-199 now records its composition with the general term-reader boundary. The release audit matched all 76 numbered ADR files to 76 unique index targets. Seventy-two decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision template. The previously delayed ADR-0063 remains implemented by FTR-187's bounded post-open word-filter maintenance and its accepting, refusing, unchanged, cancellation, and lifecycle tests. No accepted or queued ADR implementation remains knowingly outstanding.

Hundreds of simultaneous successful requests remain a horizontal capacity requirement rather than a claim about this four-processor production node. A future read tier must give each replica independent processors and I/O, an independently owned immutable search generation, and a query-ready document projection. Routing must admit only ready replicas inside the freshness bound, include queue time in the measured latency objective, and retain the target with one replica unavailable. Multiple processes must not share one live mutable Scorch directory. That runtime boundary requires a separate accepted and implemented topology ADR with synchronized Docker, systemd, package, rollout, and rollback changes.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.54 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.54`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.54 identity, health, readiness, indexed document total, stable restart count, bounded logs, and resource counters. Exercise genuinely new sequential local queries, synchronized result-bearing probes, and repeated controls while observing queue-inclusive latency and post-response CPU before accepting search.
5. Start `yago-crawler` only after node search acceptance passes. Confirm its connected state and new logical session, then prove manual and web-ingest crawl-order progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.53, stop both services, install the exact published v0.0.53 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores the observed late term-reader behavior.

## Known limitations

- Production success remains unconfirmed until the published v0.0.54 Debian package is deployed and genuinely new sequential and synchronized local searches complete within the operator budget before the crawler is started.
- One active Bleve term-reader construction, `Next`, `Advance`, optimization, or close step cannot be interrupted inside Bleve. The wrapper checks the context immediately after that step and refuses all later term-reader work.
- One four-processor process is not validated for hundreds of complete HTTP requests with live projection, evidence, peer work, and response encoding. Sustained hundreds-request service needs separately implemented and measured horizontal read capacity with independent CPU, I/O, immutable index generations, query-ready document projections, freshness-aware routing, queue-inclusive admission, and one-replica-loss capacity.
- Same-host processes sharing the current four processors are not additional capacity. Multiple processes must not open one live mutable Scorch directory. Immutable index-generation distribution and replica-aware routing are not part of this release.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class, and deployed releases show no recurrence of its corrupt-frequency OOM symptom. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
