## Abstract

YaGo v0.0.28 makes a partial failure mean exactly one thing. The Tavily `/search` endpoint scored availability after the caller's own date, domain, and exact-match filters, so a request that narrowed its result set to zero was refused outright; all thirty-nine authenticated searches over six hours were refused while the YaCy surfaces answered the same queries with ten results. A query the swarm cannot be asked, a fan-out cut by the deadline, and a call this node cut itself are each now named for what they are. An answer the node cannot vouch for is HTTP 409, not 503: the search ran, and part of the swarm did not answer.

## Changes

### Availability is decided on what the sources returned, not on what the caller kept

- `POST /search` passed the post-filter result count into its availability test. The date, domain, and `exact_match` filters run between retrieval and that test, so "your own constraints matched nothing" became indistinguishable from "a source did not complete" and was answered HTTP 503 with `Retry-After`: advice to retry a query whose outcome is fixed by the query itself.
- The production evidence is unambiguous. Over six hours every one of the thirty-nine authenticated `/search` requests returned 503, with durations between 1538 ms and 4751 ms, while `/yacysearch.json` and the public portal returned HTTP 200 with ten results for the same queries. The node's own log records `results=10 partialFailures=2` and then `status=503` for a single search: ten results were retrieved and none survived to be counted.
- The endpoint now scores the retrieval outcome, which is what the sibling `searchCompletion.errorForCaller` on the same error path already did. The parameter is named `retrievedCount` and its contract is stated where it is read.
- The amplifier is structural rather than incidental: no search observed on the reference deployment in thirty hours completed with zero partial failures, and the median was eighteen. On a live swarm node the "at least one partial failure" precondition is effectively always satisfied, so every empty answer for any reason reached the refusal.

### An answer the node cannot vouch for is a conflict, not an unavailable service

- The refusal that remains carried HTTP 503. That code asserts the endpoint itself could not serve the request, which is false here: the search ran inside its budget and returned, and only part of a federated backend failed to answer. Tavily-compatible client libraries raise on 5xx, so the status made every such answer an exception in the caller rather than an empty result set, on the most ordinary outcome a young index has.
- The refusal is now HTTP 409 with the same `search_unavailable` code, body, and `Retry-After`. The condition is a conflict with the current state of the swarm, not a property of the request, so no 4xx code that blames the request content would be accurate either; 409 is the one that describes state rather than syntax.
- 503 is left to mean what it says on this surface. The capacity and admission refusals in `search_access.go`, `search_admission.go`, `node_tavily_search_admission.go`, and `raw_content_admission.go` are unchanged and still answer 503 with `Retry-After`, and their existing tests pin that separation.

### A query the swarm cannot be asked is not a lost peer

- The DHT is a word-hash lookup, and `ParseTextQuery` consumes `site:`, `inurl:`, and `tld:` as modifiers. A query of `site:example.com` therefore arrives at the remote stage carrying no word hashes: nothing was sent, no peer was reached, and nothing timed out. That fact was reported as `remote-yacy`, indistinguishable from a peer that failed.
- `PartialFailureSourceQueryShape` now marks a stage that had nothing to ask because of the caller's query. The reason text is unchanged, so the operator's diagnosis is preserved on every surface that displays it.
- `Response.LostSourceFailures` counts only the failures that stand for a source the node could not get an answer from, and every availability decision reads it: `UnprovenZero`, both Tavily gates, and the session layer's exhaustion test. The session layer had to move as well -- an unexhausted session is on its own enough to make every empty page read as an answer the node cannot vouch for, so leaving it would have kept the defect on `/yacysearch.*` while fixing it on `/search`.
- The applicability guard is decided on the word-hash count rather than the term count, because `termHashes` discards blank terms: a request carrying only whitespace has terms and no hashes. The now-unreachable branch in `remotePeers` is deleted rather than left as dead code.
- A node with no peers, no peer source, or no DHT targets for a term keeps counting as a lost source. That query was routable and the peers were missing, which is transient and state-dependent, so the retry advice is honest. Only a query that could not be asked at all is reclassified.

### A truncated fan-out no longer looks complete

- `searchVariants` stops on a finished context, and the passes it had not yet run produced neither a result nor a partial failure. A fusion missing them was byte-identical to a whole one, so an empty result read as a truthful zero and the session layer could store it as a settled result set. The unrun passes are now counted and reported against the local remote stage, because the deadline is this node's own or its caller's, never the swarm's.

### A call this node cut itself is not the peer's failure

- When this node's outbound response budget ran out or its admission gate was cancelled, sometimes before the peer was contacted at all, the resulting partial failure was stamped with the peer's hash. `peerSearchFailureTotal` counts distinct peer hashes, so this node being busy inflated the count of peers that failed and the console blamed a healthy peer.
- `recordPeerFailure` already kept these two causes out of the peer's reputation. Both it and the partial failure now read one `locallyCutRemoteCall` predicate, so the two attributions cannot drift apart, and the failure is attributed to the local remote stage.

### The public portal stops contradicting its own hint

- The portal derived its incomplete banner from the raw failure count. A modifier-only query therefore printed `Some enabled search sources were unavailable ... Please try again` directly above the hint telling the reader to add a search word. Nothing was unavailable and no retry helps. The banner now reads the lost-source count.
- `SourceLabel` passed the raw `query-shape` identifier through to the portal, the Admin search page, and the explanation console, which name components an operator can inspect; it would have read as a subsystem that does not exist. It renders as a phrase describing the query, exactly as `ddgs` already renders as `web` on those surfaces.

### A HIGH-severity text-normalization denial of service is closed

- `golang.org/x/text` v0.38.0 carries CVE-2026-56852: `norm.Iter` can enter an infinite loop on crafted input. The dependency is indirect in every module that has it, and this project feeds attacker-controlled page text through Unicode normalization on the crawler ingest path, so the loop is reachable rather than theoretical. All five affected modules move to v0.39.0, which carries the fix. The finding is pre-existing rather than introduced here; it was caught by the release scan and would have failed the tag workflow's HIGH/CRITICAL gate.

### A peer roster assembled without its sampler no longer faults

- `observedPeerRoster.observe` took the sampling mutex through the `sampler` pointer, and only `observePeerRosterWithClock` installs one. A struct literal assembled anywhere else faulted on its very first observation with a nil-pointer dereference. A roster without a shared sampler now counts through a private one: it cannot ration the all-shard read across copies of the roster, which is the only thing sharing buys, and it cannot crash. This closes a limitation recorded in the v0.0.27 memo.

## Compatibility

- No environment variable, Admin setting, route, request field, response field, public schema, listener, port, service, image name, package path, Bleve mapping, document encoding, or deployment topology changes. No contract or wire-format change.
- One dependency change: the indirect `golang.org/x/text` moves from v0.38.0 to v0.39.0 in `yagonode`, `yagocrawlcontract`, `yago-crawler`, and both end-to-end test modules. It is a patch-level upstream release carrying a security fix and no API change.
- One additive value in an existing field: `partialFailures[].source` can now carry `query-shape` on the surfaces that already serialize partial failures. A reader that treats the source as an opaque string is unaffected; a reader that switches on known sources sees an unrecognised one, as it already may for a peer hash.
- `POST /search` changes two status codes. A request whose own filters matched nothing, and a query the swarm could not be asked, now return HTTP 200 with an empty result list instead of 503. The remaining refusal -- nothing retrieved at all and at least one genuinely lost source -- returns HTTP 409 instead of 503, with the same `search_unavailable` error code, the same body, and the same `Retry-After`. This is a breaking change for a client that switches on 503 or that treats only 5xx as retryable; a client reading the error code or the response body sees no change. On a live swarm node the 409 case remains common, so a query with no local hit and a failed peer still refuses.
- HTTP 503 on `/search`, `/extract`, and the raw-content path now means only what it says: the node refused the work on capacity or admission grounds. Those responses are unchanged.
- `/yacysearch.*` keeps HTTP 200 and its YaCy body shape. The advisory `X-Yago-Search-Availability` header and the `yacy:partialFailure` element are unchanged in form; a query-shape failure no longer triggers the header, and a truncated morphology fan-out now does.
- `site:example.com` answers HTTP 200 with an empty list instead of 503, and still returns nothing. A modifier-only query matches nothing in the local index either, because parsing leaves its term list empty and the strict term query then falls back to an empty query string. Host-only browsing is an unimplemented feature, not a regression introduced here.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.28 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.28`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first, then `yago-crawler` after node readiness. Verify both versions, `/health`, `/ready`, and the configured listeners. Readiness on a large index takes minutes: the reference deployment opens eight vault shards and loads its word filter in about 153 seconds before it accepts connections.
5. Probe `POST /search` with a request whose filters exclude everything, for example a `time_range` bound against an index with no dated documents. It must answer HTTP 200 with an empty result list and no `Retry-After`. Any refusal there means the release did not take. Confirm separately that a query with no local hit still refuses with HTTP 409 and not 503, and update any client or monitor that treats 503 as the search-incomplete signal before enabling traffic.
6. Keep production verification observation-only.

For rollback, stop crawler and node, reinstall the v0.0.27 package, start and verify the node, and then start the crawler. No index rebuild or data restore is required. The older node resumes refusing a request whose own filters matched nothing, resumes reporting a wordless query as a lost peer, and resumes attributing its own outbound cuts to the peer. Stored documents, sessions, and rosters remain valid in both directions; no persisted format is touched by this release.

## Known limitations

- `site:example.com` and other modifier-only queries now answer honestly but still answer nothing. Serving them requires a host-scoped retrieval path that does not depend on word hashes, in both the local index and the swarm protocol; that is a feature this release does not add.
- The availability signal on `/yacysearch.*` remains advisory. The status stays 200 for YaCy parity, so a client that reads neither the header nor the RSS element still cannot distinguish an unproven zero from an empty index. The two surfaces therefore still express the same fact differently: `/search` refuses with 409 while `/yacysearch.*` answers 200 and labels the response. Serving the Tavily surface as 200 with the same advisory header was considered and not chosen for this release.
- The structured query log still records the raw partial-failure count and source list rather than the lost-source count. That is deliberate for a diagnostic record, but an operator reading the log alongside the Admin activity view will see two different counts for one search.
- A truncated morphology fan-out is now reported, and because it is attributed to the local remote stage it also satisfies the incomplete-refresh classifier, so such a search may be served from a recent successful session instead. That is the intended recovery, but it means the truncation is visible in the failure list rather than in the served rows.
- The remaining write-gate contributors from v0.0.27 are untouched: the RWI intake transaction is still unbounded in size, the peer-reputation writer still scans every peer inside its write transaction, the transfer tally still takes a writer's mutex on its read path, and overflow trimming still runs on the synchronous hello path.
- Peers cut by the outbound call budget are now attributed correctly but query variants skipped on the swarm deadline are the only truncation this release reports; a peer dropped by the outbound budget mid-fan-out still contributes no result and its own failure only.
- The known-peer gauge remains up to five seconds stale, and after a failed sample the previous value stands for up to another interval.
