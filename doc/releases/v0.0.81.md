## Abstract

Yago v0.0.81 changes when an empty Tavily-compatible search is retryable and updates the build baseline to Go 1.26.11. After exact retrieval completes, a fuzzy-recovery deadline or a failed peer need not produce HTTP 409. Peer failures qualify only when every requested query variant has a valid completed peer answer and the remote stage has not expired. Required-source failures remain retryable. Diagnostics, incomplete-result caching rules, and YaCy-compatible search behavior are unchanged. Go 1.26.11 corrects the net/http request-body limit race reported as CVE-2026-97054. No setting, storage, or wire-format migration is required. Rollback restores the earlier availability policy and vulnerable Go baseline.

## Changes

### Empty-search availability

- Tavily-compatible `POST /search` can return HTTP 200 with an empty result list after exact retrieval completes when the remaining losses are an optional fuzzy-recovery deadline or proven partial peer loss.
- A peer failure qualifies only if at least one peer supplied a valid completed answer for each requested query variant. A valid empty answer qualifies. A secondary search over a subset of the query does not establish completion of the original query.
- Blank replies, replies without an explicit result count, incomplete replies, and truncated replies do not establish answer evidence. Their existing parsing behavior is unchanged.
- An individual peer timeout may qualify while the overall remote-search stage remains live. Expiry of the overall remote stage withdraws the exception. Evidence from one query variant cannot cover an unanswered variant, including after session failure merging.
- Web failure, total peer loss, absent or unknown answer evidence, missing targets, required exact or local failures, and remote-stage budget or capacity failures remain retryable HTTP 409 with `Retry-After: 1`. Fuzzy failures other than a deadline also remain required losses.
- Original-caller cancellation and execution errors retain their existing error paths. Complete honest misses, row-bearing partial responses, and requests whose own filters remove all retrieved rows retain their existing behavior.

### Security and build baseline

- Workspace and module directives require Go 1.26.11. Both container builders pin the same multi-architecture Go image by digest.
- This patch release corrects the `net/http` request-body limit race reported as GO-2026-6859 / CVE-2026-97054. No application dependency is added.
- Reusable-module API compatibility is checked against the published v0.0.80 source. The exception list remains empty.

## Compatibility

Tavily request fields, success fields, detail-only error envelopes, and retry headers are unchanged. The change affects whether specified optional losses make an empty result retryable; it does not add provider provenance or any public answer-evidence field.

All partial failures remain in diagnostics. Global source-completeness checks, session exhaustion, and incomplete-result caching retain their conservative behavior. The new HTTP exception does not make partial coverage exhaustive. YaCy-compatible search, the public portal, and YaCy wire endpoints are unchanged.

Search budgets, peer selection, peer reputation, web-engine selection, and operator settings are unchanged. No environment variable, listener, service topology, document format, RWI format, or crawler contract changes. Node and crawler can interoperate with the previous release, but operators should install both patched binaries together to apply the standard-library correction.

## Upgrade and rollback

1. Download the published package for the host architecture. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, source ref `refs/tags/v0.0.81`, and the commit identified by that tag.
2. Back up the configured data directory under the deployment's established backup policy. Stop `yago-crawler` and `yago-node`, then install the package with `dpkg -i`. Package installation enables services but does not start them.
3. Start `yago-node`, verify health and readiness, then start `yago-crawler` and verify its connection and work progress. No reindexing or data conversion is required.
4. If rollback is necessary, stop both services, install the attested v0.0.80 package, and start and verify the node before the crawler. Rollback restores the stricter Tavily availability policy and Go 1.26.10, including the known standard-library vulnerability. Prefer a corrective forward release where possible.

Container operators use the exact immutable `v0.0.81` image tags. Systemd and package deployments use the same binaries and runtime configuration.

## Known limitations

- This release does not eliminate every HTTP 409. Required-source failures still require a retry. No measured production reduction is claimed.
- A completed answer from some peers does not establish exhaustive coverage. Incomplete answers remain visible in diagnostics and are not cached as complete.
- Existing permissive parsing of blank or incomplete peer replies remains unchanged; such replies do not grant the new peer-loss exception.
- The mandatory release-scope review found one open issue with the exact `bug` label and none with the exact `enhancement` label. [D4rk4/yago#3](https://github.com/D4rk4/yago/issues/3) was reviewed and left open: no memory leak or pressure defect is confirmed by the available evidence, existing memory attribution remains available, and no safe issue-specific correction was identified within this candidate. No memory-use improvement is claimed.
