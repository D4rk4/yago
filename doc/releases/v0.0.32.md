## Abstract

YaGo v0.0.32 makes an idle crawl seeder say what it decided. Every refusal below
the searcher was silent: a live toggle that closes, a URL that will not
normalize, a page already stored, and a provider that returned nothing all left
the same trace in the journal, which is none. On the reference deployment the
seeder published nothing for hours while the provider answered normally, and
locating the cause meant reading the code and guessing rather than reading the
record. Three records now report what arrived, what was admitted, and what was
published or skipped and why.

## Changes

### The crawl seeder reports its decision

Three records replace three silences.

`web-search crawl seeding considered` reports how many provider rows reached
seeding and how many survived URL admission. That pair is the one that
discriminates: rows arriving with none admitted means the refusal happened at
admission, which is where the live `web.fallback.seed_crawl` toggle closes.

`web-search crawl seeding outcome` reports, per call, how many URLs were
published as crawl orders, how many were skipped because the page is already
stored, and how many could not be normalized into a seed URL. Skipping a stored
page is the seeder working correctly; until now it was indistinguishable from
the seeder never running.

`web-search crawl seeding gate closed` reports a direct refusal by the live
toggle. It covers the path that reaches `Seed` directly. Note that the gate also
closes earlier, inside `AdmitCrawlSeedURL`, so that admitted URLs do not consume
the bounded seed-admission slots for work that would then be discarded; on that
path `Seed` is never reached and the closed gate is visible only as the
considered record's "rows arrived, none admitted".

Every field is derived from the rows and their URLs. None carries the submitted
query, which the privacy test in this package asserts.

## Compatibility

- No environment variable, Admin setting, route, request field, response field, public schema, listener, port, service, image name, package path, Bleve mapping, document encoding, storage format, or deployment topology changes. No contract or wire-format change. No dependency change. No behaviour change: this release only records decisions that were already being made.
- Three new Info records on a node that seeds crawl from web discoveries: one per seeding consideration, one per seeding call, and one per gate refusal. An operator filtering below Info sees no change.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.32 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.32`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify the exact version, `/health`, `/ready`, configured listeners, and current logs. The vault word filter is built before the listeners open; on the reference deployment that has taken 430, 520, and 590 seconds, and readiness should be polled rather than assumed.
5. Start `yago-crawler` after node readiness. Verify its exact version, control and ingest connections, a current heartbeat, and absence of repeating lease-loss output.
6. Keep production verification observation-only.

For rollback, stop crawler and node, reinstall the v0.0.31 package, start and verify the node, and then start the crawler. No index rebuild or data restore is required; no storage format changed in either direction. The older release stops emitting the three records and the seeder becomes silent again.

## Verification

- `make verify` on the release tree: tidy, format, vet, lint, architecture, race tests, build, and coverage at exactly 100 percent of statements in all six modules (`yagonode` 46919, `yago-crawler` 12051, `yagocrawlcontract` 1265, `yagomodel` 923, `yagoproto` 517, `yagoegress` 59).
- The gate rejected the first attempt: `sloglint` refused a log key written `unusableURL` where the tree's convention, and the rest of its records, use a camelCase spelling such as `sourceUrl`. A divergent key breaks the greps an operator writes against these records, which is the opposite of what this release is for.
- Mutation testing: removing the considered record, and reporting the admitted count as the arriving count, each fail a test.
- The test asserts the discriminating pair explicitly -- two rows arriving, none admitted -- against a seeder that refuses admission, which is what a closed live toggle looks like from the searcher. It also asserts that none of the records carries the query.

## Known limitations

- This release does not fix the reported symptom. It makes the decision legible so the next change is made against a record rather than a guess. On the reference deployment, before this release, the provider returned ten accepted rows for a portal query and the seeder published nothing, with every observable step reporting healthy; which of the remaining refusals occurred is exactly what these records will now say.
- The v0.0.31 change that preceded this one -- seeding from the relevance-verified rows rather than from the rows that also survived the caller's constraints -- is a correct narrowing fix, but it does not apply to a request that carries no constraints, which is the reported case. It remains in place for constrained requests.
- The gate's early closure inside `AdmitCrawlSeedURL` means a closed toggle is reported indirectly, as a considered record with nothing admitted, rather than by the gate record. Reporting it directly would require the admission path to distinguish a refused URL from a refused gate, which this release does not add.
- The provider failures made legible in v0.0.30 remain unfixed: `mojeek` fails with a backend error and `brave` reports rate limiting, while `bing` and the DuckDuckGo engines answer.
- The corpus-signal refresh, the peer-roster write contributors from v0.0.27, and the two deferred fingerprint-read reductions from the v0.0.29 memo are all untouched.
