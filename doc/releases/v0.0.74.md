## Abstract

Yago v0.0.74 bounds the cost of long local search queries and reduces node storage commits during crawl ingest. A query that requires only some of its terms previously walked every document of every term and could exhaust the 1.8-second local search deadline, serving partial or empty results. Such a query now walks only documents containing its rarest terms; the matched documents are unchanged. Anchor-target pages grow from 16 to 256 URLs and storage updates from 32 to 512 rows. A failed inbound-anchor refresh no longer loses its retry mark. No setting, environment variable, listener, message shape, storage format or dependency changes. Node and crawler may be upgraded in either order; rollback to v0.0.73 needs no conversion.

## Changes

### Rare-term-driven partial-coverage matching

Local search can accept a document that contains only some of the query's optional terms. A coverage rule sets how many of them must be present, both for the main query and for the per-analyzer branches. Before this release, the node evaluated such a rule by walking the document list of every term in full, so a query that included common words visited most of the corpus. On the production node, a query of about ten terms cost about four CPU-seconds and exceeded the 1.8-second local search deadline. The response then carried only the shard results completed in time, or none.

A document that contains at least m of n optional terms must contain at least one of the n − m + 1 terms with the lowest document frequency. When the rule requires at least two terms, the node now enumerates only documents that contain one of those rarest terms. It checks each candidate against the other terms in ascending document frequency and rejects it as soon as the remaining terms can no longer meet the requirement. Common terms are consulted only at those candidates. Scoring uses the same disjunction scorer, so the matched documents and their total count are unchanged. Rules that require zero or one term keep the previous evaluation. Mixed letter-and-digit identifier terms remain mandatory, as before.

On a synthetic 200,000-document index, an 11-term relaxed query fell from about 720 ms to about 160 ms. Strict queries were unchanged at about 12 ms. The production effect had not been measured when this memo was prepared.

### Larger anchor-target storage pages

Crawl ingest projects outbound-anchor targets in sorted pages of at most 256 exact URLs instead of 16. One target storage update holds at most 512 physical rows instead of 32. The 8 MiB encoded byte limit is unchanged, so large anchor data still splits a page. Up to 256 linked targets of one delivery group therefore commit in one storage update, within the row and byte limits, where they previously needed one update per 16 targets.

The background inbound-anchor refresh keeps its 64-target page, because it re-indexes while it holds the page's target locks. Each of its two phases now commits a full page in one storage update instead of two. The production write-volume effect had not been measured when this memo was prepared.

### Inbound-anchor refresh keeps retry marks across shard commits

In v0.0.73, one refresh update stored a target's refreshed document and removed its refresh mark. Documents and marks can live on independently committed shards, so the mark deletion could commit while the document commit failed. The target then kept stale inbound anchors without a retry mark, and a restart did not recover it.

A refresh now commits all of a page's changed documents first. Only after they succeed does it remove the page's marks, in separate mark-only updates that use the same row and byte limits and keep the same target locks. An index or document-commit failure keeps every mark of the page for a later pass, including after reopening. A failure while removing marks may leave already-current targets marked; a later pass removes those marks without rewriting or re-indexing their documents. A missing or unchanged target still loses its mark without a document write; deleting the mark remains a storage write. These steps are not atomic across shards.

New fault tests on a real sharded vault cover these failure paths. They also prove that replaying an ingest whose anchor-row and mark update committed only partly restores consistent anchors and marks after reopening.

### Documentation

- The v0.0.73 memo gained two factual corrections dated 2026-11-04. They describe how that release can lose a refresh mark after a partial shard commit, and how indexing can precede a failed document commit.
- The specification states the 512-row limit for both refresh phases.

## Compatibility

- No YaCy, Tavily or node-crawler message shape or status code changes.
- Node and crawler from this release interoperate with the v0.0.73 node and crawler; they may be upgraded in either order.
- No storage collection, record format or index mapping changes. Existing data needs no conversion.
- Local search returns the same documents and total counts for every query. Scores of partial-coverage queries can differ in the last floating-point digits, because term contributions are summed in document-frequency order. Results with practically equal scores may therefore change places.
- No setting, environment variable, listener, port, service or dependency changes. The Compose and systemd deployment examples are unchanged.

## Upgrade and rollback

- Upgrade the node and crawler in either order. On a generic bare-metal host:
  1. Fetch the release `.deb` and verify its artifact attestation against repository `D4rk4/yago`, the release workflow, tag `v0.0.74` and its source commit.
  2. Back up `/opt/yago/data`.
  3. Stop `yago-node` and `yago-crawler`.
  4. Install with `dpkg -i`.
  5. Start both services and confirm they report healthy.
- Rolling back to v0.0.73 needs no data conversion. It restores the v0.0.73 behavior: full document-list evaluation of partial-coverage queries, smaller anchor-target pages, and the possible loss of a refresh mark after a partial shard commit.

## Known limitations

- The production latency effect of partial-coverage matching had not been measured when this memo was prepared.
- A query whose rarest terms are themselves common still walks large document lists.
- Single common-term queries, which cost 0.5 to 1.1 seconds on the production node, are not addressed.
- Neither v0.0.73 nor this release has demonstrated lower production write volume.
- Refresh phases are not atomic across shards. Search may show a target's previous anchor text until its refresh completes; failed passes and backlogs extend that delay.
- Bug #3 (node memory use) remains open; this release does not change memory behavior.
