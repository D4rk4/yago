## Abstract

Yago v0.0.80 makes PDF and PostScript reading stop when its caller's time runs out. Before this release, the shared `yagopdf` reader kept decoding after a deadline had passed. Peer snippet rescue therefore overran its 200 ms budget, fetch-on-extract overran its fetch timeout, and the crawler had no PDF or archive time limit. Now decoding and text reading stop on the reading goroutine at the caller's deadline. The crawler stops reading a PDF or PostScript file after 5 seconds and stops opening archive entries after 5 seconds. Node and crawler may be upgraded independently. No setting, storage, extraction generation, or YaCy wire change is required. Rollback to v0.0.79 needs no conversion.

## Changes

### Reader

- `yagopdf` adds `ReadPDFContext`, `ReadPostScriptContext` and `ErrNoReadableText`. Both functions read exactly as `ReadPDF` and `ReadPostScript` do, but stop when the caller's context is cancelled or its deadline passes.
- A stopped read returns the context error and no text. A file without readable text returns `ErrNoReadableText`. Callers can therefore tell an unreadable file from a read they gave up on.
- The stop is checked inside the existing decoding budget and text limit, so reading ends on the caller's own goroutine. No background goroutine is started and none is left running.
- `ReadPDF` and `ReadPostScript` keep their signatures and results.

### Node

- Fetch-on-extract passes its fetch timeout to the PDF reader. A PDF still being read when the timeout passes is reported in `failed_results` with the same message as any other fetch failure.
- Peer snippet rescue uses the same PDF reading path, so a slow PDF no longer holds the pass past its 200 ms budget. As with other fetch failures, a remote row without visible evidence is removed and `TotalResults` is reduced.

### Crawler

- A PDF or PostScript file still being read after 5 seconds produces no indexed document. Crawl progress counts it as failed because the content parser produced no indexable document.
- An archive container opens no new entry once 5 seconds have passed since its first entry began. Text from entries read before that point is kept.
- Both limits are fixed. No environment variable or admin setting is added.

### Release engineering

- The reusable-module API baseline moves to `v0.0.79`. The `v0.0.78` exception for `CurrentExtractionGeneration` is removed because it no longer applies.
- Two pre-existing NilAway findings in `yagopdf` moved by a few lines. The baseline records their new locations; no finding was added or removed.

## Compatibility

- YaCy wire: unchanged.
- Tavily-compatible API: request and response shapes are unchanged. A PDF that cannot be read within the fetch timeout is now listed in `failed_results`; previously the request waited for the read to finish.
- Node-crawler messages: unchanged. The extraction generation stays at 2, so this release causes no refetch.
- Storage: no collection, record format, or index mapping changes.
- Reusable-module API: additive only. The `yagopdf` additions are new exported names; no existing exported name changes. Modules covered by the API compatibility gate have no exported API changes against `v0.0.79`.
- Settings: no environment variables or admin settings are added, removed or changed. No listener, port, or service changes.

## Upgrade and rollback

- Node and crawler may be upgraded independently; each carries its own part of the change. On a generic bare-metal host:
  1. Fetch the release `.deb` and verify its artifact attestation against repository `D4rk4/yago`, the release workflow, tag `v0.0.80` and its source commit.
  2. Back up `/opt/yago/data`.
  3. Stop `yago-node` and `yago-crawler`.
  4. Install with `dpkg -i`.
  5. Start both services and confirm they report healthy.
- Rolling back to v0.0.79 needs no data conversion and causes no refetch. PDF reading then again continues past its caller's deadline.

## Verification

All checks below ran on the release source unless stated otherwise.

- `make verify` passed. It covers module tidiness, formatting, vet and lint, gosec, the NilAway ratchet, API compatibility against `v0.0.79`, govulncheck, race-instrumented tests, the recorded test shuffle, bounded fuzz smoke, 100% statement coverage in every module, and builds.
- New tests check each limit in both directions with synthetic fixtures: reading succeeds under a generous deadline and stops under an expired one. They also check that an unreadable file is reported as unreadable, not as a timeout, and that a readable PDF without the search term is dropped without a failure.
- On a synthetic 64-stream compressed PDF, peer snippet rescue took 726 to 878 ms without the change and about 202 ms with it. Synthetic decoding-heavy PDFs that took 0.24 to 0.95 s without a deadline stopped 10 to 14 ms after reading began under a 10 ms deadline. A reader benchmark showed no measurable cost from the stop check.
- Dockerized Semgrep 1.168.0 reported no findings. Dockerized Trivy 0.72.0 reported no HIGH or CRITICAL vulnerability, secret, or misconfiguration finding in the source tree or in the locally built `yago-node` and `yago-crawler` images.
- `make e2e` passed with locally built current-source images: 20 node tests, including interoperability with a real Java YaCy peer, and 8 crawler tests. These include restarting the node while the crawler keeps running and restarting the crawler while the node keeps running, with crawl work continuing after each restart.
- Release text and fixtures were checked for operator input; they contain only synthetic values and aggregate measurements.

## Known limitations

- Locating objects, decrypting, and walking the page tree run to completion before the deadline is checked. Their cost grows with file size: about 100 to 125 ms on 8 MiB synthetic files. Response size limits bound this work.
- The crawler's 5-second limits are fixed and cannot be changed at runtime.
- An archive entry that has already started is read to its end; the archive limit applies between entries.
- Open issue #3 (node memory use) was reviewed for this release and is not addressed. It concerns memory accounting, which is outside the scope of this change; no new information from the reporter's host is available.
