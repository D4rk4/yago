## Abstract

YaGo v0.0.43 corrects the remaining cold-search regression after v0.0.42. Stored-candidate validation now groups exact document-location and row-presence reads by physical vault shard and reads independent shards concurrently without sharing bbolt transactions. A disposable cold-cache test improved 100 two-phase lookups by 2.85–3.30 times while preserving order, cancellation, legacy fallback, and exact row authority. No data migration, dependency, setting, wire shape, or deployment-topology change occurs. Upgrade and rollback with v0.0.42 are data-compatible; production confirmation remains required after published-package deployment.

## Changes

### Read exact candidate presence by physical vault shard

v0.0.42 limited each document-presence snapshot to the candidate page requested by its caller. The public session layer asks for 51 rows to retain one lookahead result, and the lexical ranking layer expands that request to its bounded 100-candidate window. The document vault therefore still performed up to 100 sequential location reads followed by up to 100 sequential exact-row checks before a cold local result could complete. The production node answered repeated queries after those mmap pages became resident, but previously unseen common queries still exhausted the fixed interactive deadline.

Typed vault keyspaces now expose an optional ordered set-read boundary for values and presence. The production sharded vault groups supplied keys by their current physical routing, opens one independent read-only transaction for every touched shard, and assigns one goroutine to each transaction and bucket. A transaction or bucket is never shared between goroutines. Each shard reads its keys serially, every reader joins, results return in the caller's original order, and a simultaneous failure resolves deterministically by routed shard. Engines without this capability retain the established per-key compatibility path.

Document presence remains an exact two-phase decision inside one URL read-lock scope and one logical vault view. Location values are decoded first. Their derived ordered-document keys are then checked for actual row presence; identities without a location retain the legacy URL-key check. A location marker is routing evidence only and cannot make an absent document appear present. Value checksum and compression decoding, duplicate identity handling, missing-row semantics, context cancellation, and transaction error latching remain intact.

The work is bounded by the requested key set and the physical shards it touches. It adds no background prefetch, cache, format migration, setting, or dependency. Bleve candidate scoring, overfetch, result order, totals, snippets, facets, post-filters, and full-document compatibility hydration are unchanged.

### Close the ADR implementation inventory

The release gate inspected every numbered ADR and its index entry. The 66 files comprise 62 live Accepted decisions, three records explicitly Superseded by later decisions, and the non-decision ADR-0000 proposal template. The previously queued serving-boundary work in ADR-0063 is present in the runtime: conservative RWI filters are installed before serving, one owned worker reads 4,096-row snapshots, yields to interactive demand, retains a conservative answer on failure, joins on close, and is scheduled after split and compaction. Its complete unit, race, lifecycle, and production-startup evidence remains green.

ADR-0065 records the new physical-shard exact-presence boundary and is implemented by this release. References to deferred or future work in other Accepted records describe rejected alternatives, explicit non-goals, or known limitations such as optional eviction-time redistribution, persisted fuse filters without freshness evidence, online shard splitting, and a two-strike dead-page policy. They are not unimplemented parts of those accepted decisions. No Accepted or queued ADR implementation remains knowingly outstanding.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.43 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.43`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Wait for exact v0.0.43 identity, health, readiness, stable restart count, and bounded logs. Exercise several never-before-used common queries before repeating them so acceptance covers both cold and warm paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm a new logical session, continued crawl and index progress, DDGS behavior under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.42, stop both services, install the exact published v0.0.42 package, and start the node before the crawler. The stored and derived-index formats are identical, so no rebuild is expected. The v0.0.42 sequential cold-query regression returns with that rollback. Rollback to v0.0.38 retains the generation-v2 boundary and follows the complete derived-index rebuild procedure documented by v0.0.41.

Eight additional never-before-used common queries each returned zero and incomplete in 1.953–1.966 seconds. The crawler remained inactive and production data was not changed.

Each measured round closed the vault, applied `POSIX_FADV_DONTNEED` to every shard file, and reopened it before checking 100 exact two-phase identities. ## Known limitations

- Production success remains unconfirmed until the published v0.0.43 Debian package is deployed and multiple genuinely cold common queries complete within the fixed interactive budget before the crawler is started.
- The speedup depends on keys reaching independent physical shards and the host storage serving those reads concurrently. Keys routed to one shard remain serial under one transaction owner. The synthetic result is evidence for the exercised boundary, not a latency guarantee for every host.
- Candidate validation still performs a location phase and an exact document-row phase. The correction overlaps independent shard work; it does not weaken the row guard, remove required reads, enlarge the search deadline, or make random I/O free.
- Published v0.0.42 remains immutable. It starts and serves correctly, but its sequential exact-presence page can still make cold common queries incomplete.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class. They do not add a general decoder allocation bound for arbitrary current-generation corruption; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
