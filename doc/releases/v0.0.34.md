## Abstract

YaGo v0.0.34 makes current Admin limits authoritative for durable automatic web and swarm crawl work. Re-publishing a URL could coalesce with an older pending or leased order, allowing its stored 250-page profile to survive a later reduction; the seeder also counted coalesced and failed publications as newly created tasks. The node now distributes named current execution limits, the crawler intersects them with stored automatic profiles, and checkpoint recovery removes over-depth and excess newest pending pages atomically. Publication reporting distinguishes created, coalesced, and failed outcomes. Manual, recrawl, protocol, configuration, listener, storage-schema, and deployment surfaces are unchanged. Upgrade node and crawler together; the release does not alter operator settings.

## Changes

### Current automatic-discovery limits govern durable work

Automatic web and swarm crawl orders are durable and idempotent by canonical URL. Before this release, the Admin page and depth values were read only while constructing a new order. If the same URL already had pending or leased work, `PublishOnce` correctly coalesced the new request into that identity, but the older stored profile retained its broader limits. An order created with 250 pages could therefore continue under 250 after the operator reduced the current value.

The crawler runtime policy now carries bounded, named execution limits for `web-fallback-seed` and `swarm-seed`. The node refreshes them after either path's depth or page value changes and after the general crawler page budget changes. When the crawler compiles a matching automatic-discovery order, it selects the smaller stored or current maximum depth, per-host page limit, and whole-run page limit. It preserves the profile handle and durable order identity, never widens an already stricter profile, and does not apply named automatic limits to manual, recrawl, or unmatched work.

### Recovery converges under the current depth and page ceiling

A runtime-policy change uses the established graceful crawler-session restart. During checkpoint recovery, the crawler first discards pending pages deeper than the compiled current depth. It then applies the compiled whole-run page ceiling by discarding excess newest pending pages through the existing durable, idempotent recovery accounting. The oldest eligible work, completed totals, visited history, provenance, profile handle, and order identity remain intact. A new seed request already beyond the compiled depth is refused at admission.

Recovery mutations are transactional. Tests prove commit rollback on failure, corruption refusal, repeat repair, exact-boundary admission, and the already-correct path. This makes a policy reduction effective for pending, leased-and-recovered, and restart-recovered automatic work without rewriting the durable broker order.

### Web-seed publication reports the actual outcome

The web-result seeder previously incremented its `published` total after every publication attempt. A coalesced duplicate and an attempt that exhausted all durable-write retries could therefore be reported as a newly created task even though no new task appeared.

Publication now returns one typed outcome: published, coalesced, or failed. The stable aggregate event reports those totals separately, alongside unusable and already-stored URLs. Coalescing remains the correct idempotent behavior; it is no longer presented as task creation, and a failed write is visible as a failure.

## Compatibility

- YaCy wire endpoints, Tavily-compatible endpoints, public search surfaces, search semantics, crawl-order identity, package paths, image names, ports, listeners, services, and deployment topology are unchanged.
- No environment variable, Admin key, default setting, third-party dependency, document schema, or index format changed. Docker Compose and systemd examples therefore require no deployed-surface update, migration, or reindex.
- `CrawlerRuntimePolicy` gains an additive repeated `AutomaticDiscoveryExecutionLimit` field. A current decoder bounds the collection, validates unique one-line profile names, and requires valid depth and positive page ceilings. An older crawler ignores the unknown field. With an older node that omits it, a current crawler leaves the stored order profile in force.
- Upgrade node and crawler together to reconcile existing automatic work. A mixed-version pair remains wire-compatible but retains the previous stored-order limit behavior.
- Manual crawls, recrawls, unmatched profiles, already stricter profiles, and the existing global crawler depth rule retain their prior semantics.
- Installation does not rewrite persisted Admin settings. The effective automatic limit after upgrade is the value the operator has actually stored, not a value inferred from an earlier report or release default.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.34 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.34`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first and wait for readiness. Confirm its exact version and configured Admin automatic-discovery values. Start `yago-crawler` only after the node is ready; verify its exact version, a new accepted logical session, current heartbeats, and crawl progress without a repeating lease-loss loop.
5. Observe the first policy synchronization and any affected checkpoint recovery. Existing automatic work must use the current named limit; publication events must distinguish new, coalesced, and failed tasks. Keep production verification observation-only after service startup.

For rollback, stop crawler and node, reinstall the v0.0.33 package, start and verify the node, and then start the crawler. No data restore is required solely for format compatibility. Pages already discarded by v0.0.34 recovery are not recreated, while remaining durable orders again use the older stored-profile behavior. Confirm the operational consequence before rollback when an outstanding order contains a broader historical profile.

## Known limitations

- Named current-limit reconciliation applies to automatic web and swarm discovery only. Manual, recrawl, and unmatched work deliberately retain the profile recorded in their orders.
- A limit reduction requests a graceful session restart. A fetch already executing may finish before recovery applies the new checkpoint boundary; the change does not forcibly terminate an in-flight HTTP or browser operation.
- Older node/crawler pairs and mixed-version pairs do not reconcile existing durable orders under the new named field even though their protobuf exchange remains compatible.
- The release enforces the current stored values but does not decide what those values should be. Operators must verify the intended Admin settings separately; package installation never substitutes a reported value for durable configuration.
