## Abstract

YaGo v0.0.37 makes Bleve rebuild-marker admission idempotent. During the v0.0.36 production recovery, an operator-staged marker was owned by root with mode 0600. Startup correctly recognized it, but generation admission unnecessarily reopened it through `os.WriteFile`; the service account received `permission denied` only after completing vault initialization. This release treats an existing marker as complete durable evidence without opening, truncating, or rewriting it. Missing markers are still created with mode 0600, and creation or inspection failures still stop startup. No dependency, protocol, setting, storage format, port, or service-topology change is introduced. Existing v0.0.36 indexes and recovery markers remain compatible.

## Changes

### Preserve an existing rebuild requirement

The first production start of v0.0.36 completed eleven vault word filters and then exited with `persist bleve rebuild state: permission denied`. This was not an out-of-memory failure. The operator had staged `/opt/yago/data/search.bleve.rebuild-required` as `root:root`, mode 0600, before the package upgrade. Generation admission observed the unstamped index and called the marker writer again. Go's `os.WriteFile` truncates an existing file before writing, so the redundant operation required write permission that the `yago` service account did not have.

Marker presence already means that a complete rebuild is required. `requireBleveRebuild` now inspects that state first and returns successfully when it exists. It invokes directory creation and `os.WriteFile` only when the marker is absent. An operator-staged or interrupted marker can therefore survive a different file owner, while the service can still remove it after a successful rebuild through its ownership of the data directory.

Tests reproduce both the direct marker call and the exact segment-generation admission call with a writer that must not be invoked. The inverse paths remain enforced: a missing marker is created, an inspection error is returned, a directory-creation error is returned, and a marker-write error is returned. Existing marker bytes remain unchanged.

### Keep the v0.0.36 search and memory corrections

The zapx v17.1.4 writer correction, pre-fix index generation guard, one 32 MiB Scorch persister worker per shard, 100,000-document merged-segment ceiling, Admin Overview memory attribution, and exact 4 GiB node lifecycle gate are unchanged. This release corrects only the durable marker transition discovered while deploying those protections.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.37 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.37`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. If a rebuild marker exists, leave it in place; v0.0.37 accepts it without a write attempt and performs the required rebuild. Wait for health, readiness, exact version, and search probes before starting the crawler.
5. Start `yago-crawler`, confirm v0.0.37 and a newly accepted logical session, then observe fetches, accepted ingest batches, index growth, search responses, restart counts, memory diagnostics, cgroup events, and bounded logs across repeated intervals.

For rollback, stop crawler and node and reinstall v0.0.36. No data restore or format conversion is required solely for this change. If the rebuild marker belongs to a different account and is not writable by `yago`, v0.0.36 can repeat the permission failure; correct its ownership before starting that older binary. A rollback to v0.0.35 or earlier additionally requires the generation-file procedure documented in v0.0.36 and reintroduces the zapx writer defect.

## Known limitations

- A missing or stale generation still triggers a complete non-resumable derived-index rebuild before listeners open. Rebuild duration and temporary I/O depend on corpus size and storage throughput; a proxy can return 502 during that maintenance interval.
- Marker existence is intentionally the recovery signal. The marker payload is not a checkpoint and does not resume partial index output; startup removes the derived index and begins the rebuild from the authoritative document store.
- The exact 4 GiB Docker gate covers the bounded test corpus. A much larger mapped vault can show high file-backed RSS and progress more slowly under reclaim; RSS alone is not a heap leak or pressure signal. Use Admin Overview together with cgroup events, swap, and host available memory.
- The v0.0.36 generation guard prevents the confirmed zapx v17.1.2 output from reaching its decoder. A general decoder allocation bound for arbitrary current-generation corruption remains upstream work in `blevesearch/bleve#2393`.
- The DHT distribution setting still requires a node restart, and full-text rebuild progress remains journal-only rather than an Admin progress control.
