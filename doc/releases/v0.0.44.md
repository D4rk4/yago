## Abstract

YaGo v0.0.44 corrects the remaining cold-search evidence bottleneck observed after v0.0.43. Disk search now hydrates its existing ten visible documents through one ordered document-set read, one URL-boundary scope, and one logical vault snapshot; independent physical shards own and execute their read transactions concurrently. Exact document identity, legacy compatibility, orphan cleanup, and deadline behavior remain unchanged. A disposable cold-cache synthetic improved this boundary by 2.03–3.31 times. No data migration, dependency, setting, wire shape, or deployment-topology change occurs. Upgrade and rollback with v0.0.43 are data-compatible; production confirmation remains required after published-package deployment.

## Changes

### Read visible search evidence as one document set

v0.0.43 made the preceding stored-candidate presence stage shard-parallel. The visible evidence stage nevertheless loaded as many as ten full documents through ten separate URL read-lock acquisitions and ten logical vault snapshots. Each document load read its location and then its exact ordered row or legacy URL row. On a cold mmap, these serial point reads could consume the remainder of the fixed interactive budget after candidate scoring had completed.

The document-store boundary now offers an optional ordered document-set capability beside the established one-document interface. The production document vault acquires all requested URL read boundaries once, opens one logical snapshot, batch-reads location values, derives exact ordered and legacy row keys, and reads those sets through the physical-shard ownership boundary introduced by v0.0.43. Every touched shard owns one read-only transaction and reader; no bbolt transaction or bucket is shared between goroutines.

Returned documents and presence decisions remain aligned with the caller's order, including duplicate identities. A row is authoritative only when its embedded normalized URL exactly matches the requested identity. Missing rows remain honest absences. A corrupt document row retains the existing compatibility behavior and is retried individually inside the same snapshot so another valid row remains usable. Malformed locations, invalid ordered identities, operational storage failures, and cancellation remain failures.

Disk search invokes this capability only for the established ten-result visible-evidence limit and does not hydrate the Bleve overfetch tail. Missing stored rows still enter the existing orphan-cleanup path. Strict candidates not enriched before a deadline retain their bounded projection, while relaxed candidates without validated passage evidence remain excluded. A document directory without the optional capability retains the previous one-document path.

The correction adds no cache, prefetch worker, background I/O, format migration, setting, or dependency. Ranking rules, result order, snippets, phrase and proximity evidence, facets, filters, totals, and public response shapes remain unchanged for the same stored population.

### Close the ADR implementation inventory

The release gate inspected every numbered ADR and its index entry. The 67 files comprise 63 live Accepted decisions, three records explicitly Superseded by later decisions, and the non-decision ADR-0000 proposal template. Every index entry resolves to exactly one numbered file.

All prior ADR files are unchanged from the fully audited v0.0.43 source. The previously queued serving-boundary work in ADR-0063 remains implemented: conservative RWI filters are installed before serving, one owned worker processes 4,096-row snapshots, yields to interactive demand, retains a conservative answer on failure, joins on close, and is scheduled after split and compaction. ADR-0066 records the new visible-document set boundary and is implemented by this release with accepting, refusing, cancellation, compatibility, and unchanged-input evidence.

Deferred or future wording in other Accepted records describes rejected alternatives, explicit non-goals, or known limitations. It is not an unimplemented part of those accepted decisions. No Accepted or queued ADR implementation remains knowingly outstanding.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.44 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.44`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Wait for exact v0.0.44 identity, health, readiness, stable restart count, and bounded logs. Exercise several never-before-used common queries before repeating them so acceptance covers both cold and warm paths.
5. Start `yago-crawler` only after node search acceptance passes. Confirm a new logical session, continued crawl and index progress, DDGS behavior under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.43, stop both services, install the exact published v0.0.43 package, and start the node before the crawler. The stored and derived-index formats are identical, so no rebuild is expected. The v0.0.43 sequential cold-evidence regression returns with that rollback. Rollback to v0.0.38 retains the generation-v2 boundary and follows the complete derived-index rebuild procedure documented by v0.0.41.

## Known limitations

- Production success remains unconfirmed until the published v0.0.44 Debian package is deployed and multiple genuinely cold common queries complete within the fixed interactive budget before the crawler is started.
- The speedup depends on requested rows reaching independent physical shards and the host storage serving those reads concurrently. Rows routed to one shard remain serial under one transaction owner. The synthetic result is evidence for the exercised boundary, not a latency guarantee for every host.
- The evidence read still performs a location phase and an exact document-row phase. The correction overlaps independent shard work; it does not weaken the row guard, remove required reads, enlarge the search deadline, or make cold random I/O free.
- Published v0.0.43 remains immutable. It starts and serves correctly, but its sequential visible-document reads can still make cold common queries incomplete.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class. They do not add a general decoder allocation bound for arbitrary current-generation corruption; that remains upstream work in `blevesearch/bleve#2393`.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
