## Abstract

YaGo v0.0.35 restores crawler liveness when a locally admitted run loses its exact node lease and adds process-memory attribution to Admin Overview. Previously the pipeline abandoned the fetched job but retained the checkpoint-backed active run; enough lost grants could occupy all active-run slots and stop later DDGS-discovered work. The crawler now suspends only the matching lease-bound run, retains its checkpoint, releases admission, and leaves a concurrently rebound lease untouched. Overview reports node RSS split into anonymous, file-backed, and shared resident memory plus Go heap objects. No setting, protocol, storage format, port, or deployment topology changes. Upgrade both binaries together. The memory view is diagnostic and does not establish the cause of issue #3 on the reporter's host.

## Changes

### Lost lease grants no longer retain active-run admission

The web-search provider and node-side publication path remained healthy during the observed v0.0.34 production incident, but the crawler stopped fetching later DDGS-discovered work. A read-only copy of the node broker contained 2,354 pending orders. A read-only copy of the crawler frontier contained 97 unfinished checkpoints, and 96 checkpoint provenances matched 96 pending automatic-discovery orders.

The crawler pipeline could receive a frontier job after that run's exact local lease grant had disappeared. It abandoned the individual job and then waited for a grant change. The durable checkpoint correctly kept the run recoverable, but the corresponding in-memory run retained active-task admission. Repeated losses could therefore occupy every active-run slot with parked work, preventing the pipeline from reaching later broker orders. The failure was downstream of DDGS result retrieval and node-side seed publication.

The pipeline now asks the frontier to suspend an ungranted run. Under the frontier lock, suspension succeeds only when the job still matches the run's exact lease. It returns the in-memory pages, marks the provenance suspended, drains queued work, settles the active run, and releases its admission while leaving the durable checkpoint available for broker-authorized replay. If the run has already rebound from the stale lease to a confirmed replacement lease, the stale job cannot suspend it and normal processing continues.

### Overview attributes node process memory

The existing `/admin/overview` status region now refreshes five process-local readings every 15 seconds:

- Process resident set (RSS): all resident `yago-node` pages reported by Linux as `VmRSS`.
- Anonymous RSS: resident anonymous pages reported as `RssAnon`; this commonly includes Go heap and stack pages but is not a Go-only measurement.
- File-backed RSS: resident file mappings reported as `RssFile`; this can include bbolt and Bleve mappings as well as binaries and libraries, but it does not attribute pages to an individual file.
- Shared-memory RSS: resident shared mappings reported as `RssShmem`.
- Go heap objects: `/memory/classes/heap/objects:bytes`, the Go runtime's live and not-yet-freed object allocation measure.

The four Linux values come from one `/proc/self/status` snapshot. Each reading becomes `Unavailable` independently when its source is absent, malformed, or outside the signed display range. The page states that RSS is the sum of the three resident classes and that Go heap objects are not an additional RSS component. The complete no-JavaScript Overview and its htmx fragment use the same typed source. The System Monitor shelf, ten-second history ring, and Prometheus metric set are unchanged.

3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first and wait for readiness. Confirm its exact version and the five readings under Admin → Overview → Memory diagnostics. Start `yago-crawler` only after the node is ready and confirm its exact version and a new accepted logical session.
5. Observe broker delivery, crawler fetches, accepted ingest batches, and indexed-document growth across repeated intervals. Confirm that lease-loss records do not repeat, DDGS-discovered work progresses, both services remain on one process each without restart, and health and readiness remain successful.

For rollback, stop crawler and node, reinstall the v0.0.34 package, start and verify the node, and then start the crawler. No data restore is required solely for format compatibility. The new Overview breakdown disappears after rollback, and a future exact-grant loss can again retain active-run admission under the older crawler. Preserve the checkpoint and broker state rather than deleting work to conceal that condition.

## Known limitations

- The new readings are current node-process snapshots, not durable time series. Use the existing Prometheus process series for history and alerting.
- `RssFile` distinguishes file-backed resident pages from anonymous memory but does not identify which file owns those pages or whether the kernel can reclaim them without I/O. `/proc/self/smaps` or equivalent host evidence remains necessary for exact mapping attribution.
- Go heap objects are an allocation measure, not a resident-memory measure and not an additional part of RSS. They may differ from anonymous RSS because the Go runtime also owns stacks, metadata, reserved spans, and released or nonresident pages.
- The Overview does not measure `yago-crawler`, Firefox child processes, cgroup `memory.current`, host page cache, swap, pressure-stall information, or OOM events. These remain deployment-level diagnostics.
- Issue #3 reports only a v0.0.32 screenshot. Without measurements from that host, neither a heap leak nor the file-backed mapping pattern observed on the separately operated v0.0.34 `yagoseek.dev` node can be attributed to the reporter's system.
