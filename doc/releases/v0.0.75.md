## Abstract

Yago v0.0.75 reduces the CPU cost of opening local search queries. A production profile of v0.0.74 under long-query load attributed about 12% of node CPU to recomputing term document frequencies while query terms were ordered by rarity. The recomputation happened in the partial-coverage matcher and in the search library's term conjunctions. Each term reader now computes its document frequency at most once per search. Matched documents, total counts and scores are unchanged. No setting, environment variable, listener, message shape, storage format or dependency changes. Node and crawler may be upgraded in either order; rollback to v0.0.74 needs no conversion.

## Changes

### Term document frequencies are computed once per search

The document frequency of a term is the number of live documents that contain it. The search library computes it on demand by intersecting the term's document list with the deleted-document set of every index segment, so each computation costs time proportional to the term's document list.

Local search orders query terms by document frequency in two places. The partial-coverage matcher introduced in v0.0.74 sorts its terms from rarest to most common. The search library sorts the clauses of every term conjunction the same way. In v0.0.74 both sorts recomputed the frequencies on every comparison. A 30-second CPU profile of the production node under long-query load attributed 13.3% of node CPU to frequency computation; 89% of it was such repeated computation.

Every term reader opened by local search now computes its document frequency on the first request and returns the stored value afterwards. The partial-coverage matcher also reads each term's frequency once when it opens. A term reader whose search has passed its deadline still reports zero documents, as before. The production latency effect had not been measured when this memo was prepared.

## Compatibility

- No YaCy, Tavily or node-crawler message shape or status code changes.
- Node and crawler from this release interoperate with the v0.0.74 node and crawler; they may be upgraded in either order.
- No storage collection, record format or index mapping changes. Existing data needs no conversion.
- Local search returns the same documents, total counts and scores for every query. Frequencies are unchanged during a search, so the stored values equal the recomputed ones and terms are ordered as before.
- No setting, environment variable, listener, port, service or dependency changes. The Compose and systemd deployment examples are unchanged.

## Upgrade and rollback

- Upgrade the node and crawler in either order. On a generic bare-metal host:
  1. Fetch the release `.deb` and verify its artifact attestation against repository `D4rk4/yago`, the release workflow, tag `v0.0.75` and its source commit.
  2. Back up `/opt/yago/data`.
  3. Stop `yago-node` and `yago-crawler`.
  4. Install with `dpkg -i`.
  5. Start both services and confirm they report healthy.
- Rolling back to v0.0.74 needs no data conversion. It restores the repeated frequency computation.

## Known limitations

- The production latency effect of this release had not been measured when this memo was prepared.
- Opening term readers across many index segments remains a large share of search CPU.
- A query whose rarest terms are themselves common still walks large document lists.
- Single common-term queries are not addressed.
- Bug #3 (node memory use) remains open; this release does not change memory behavior.
