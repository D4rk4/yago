## Abstract

Yago v0.0.53 stops disk fuzzy vocabulary enumeration when its request context expires. Production v0.0.52 could return an incomplete search while Bleve continued enumerating fuzzy terms and retained native admission, delaying later reads. A per-request reader wrapper now checks context around every term step, preserves supported fuzzy and BM25 capabilities, and closes synchronously; exact and in-memory searches are unchanged. On a disposable production-index copy, a 125-millisecond fuzzy timeout returned in 143.5 milliseconds instead of 356.6 milliseconds. APIs, formats, settings, and topology are unchanged; rollback requires no rebuild. This prevents the observed late work but does not prove one four-processor node can satisfy hundreds of complete requests. Production acceptance still precedes crawler startup.

## Changes

### Stop fuzzy vocabulary walks at their request deadline

Release v0.0.52 removed the former whole-search native admission convoy, but production acceptance still failed. Seven of eight new sequential local terms returned an incomplete answer after 1.801 to 1.817 seconds. A new `endocrinology` request returned after 1.825 seconds with approximately 0.24 CPU-seconds, two minor faults, no major fault or physical input, and most of its additional work occurring after the response. Its immediate repeat completed in 83.6 milliseconds.

A separate `paleoneurology` probe isolated the bounded fuzzy-recovery stage. Exact retrieval completed with an honest miss, fuzzy recovery returned its explicit timeout after 180.75 milliseconds, and node threads continued work after the response. That work retained native-page admission even though it could no longer contribute to its caller.

Bleve v2.6.1 constructs fuzzy searchers by repeatedly reading applicable field dictionaries. Its candidate loop does not inspect the supplied context between `FieldDict.Next` calls; current upstream main has the same boundary. `SearchInContext` therefore cannot stop that construction loop at its caller's deadline.

Disk fuzzy requests now receive a per-request IndexReader boundary. Every field dictionary checks the request context immediately before and immediately after each underlying term step. Cancellation before searcher construction opens no reader; cancellation before a dictionary step performs no read; cancellation during a step returns after that step and permits no later step. Bleve's normal synchronous close path remains authoritative, so no detached query goroutine retains a native-page token after the fuzzy call exits.

The boundary preserves the base reader contract and exposes optional fuzzy-automaton and BM25 capabilities only when the underlying reader supports them. Existing dictionary errors, close behavior, cardinality, byte accounting, automata, field cardinality, scores, identities, and ordering remain authoritative. The ordinary requested-hit and complete filtered or faceted disk paths use the boundary. Exact, morphological, relaxed, and in-memory query identities remain unchanged.

The hard bound is one active `Next` call plus normal close latency because the current Bleve interface cannot interrupt a term step already executing. On the disposable production-index copy, the same production-shaped fuzzy page with a 125-millisecond context returned in 356.6 milliseconds before the boundary and 143.5 milliseconds after it, carrying the same deadline failure.

ADR-0074 records this boundary and amends ADR-0073. FTR-199 records the implemented capability. The release audit matched all 75 numbered ADR files to 75 unique index targets. Seventy-one decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision template. No accepted or queued ADR implementation remains knowingly outstanding.

Hundreds of simultaneous successful complete requests remain a horizontal capacity requirement. The cancellation boundary is request-local and adds no shared lock, goroutine, or service, so it remains compatible with independent read replicas. A replicated tier still requires a separate accepted topology ADR covering immutable generation ownership, freshness and health routing, queue-inclusive load measurement, one-replica-loss capacity, deployment, rollout, and rollback. Multiple processes sharing the current four processors or one live mutable Scorch directory are not additional capacity.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.53 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.53`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify exact v0.0.53 identity, health, readiness, indexed document total, stable restart count, bounded logs, and resource counters. Exercise genuinely new sequential local queries, synchronized result-bearing probes, and repeated controls before accepting search.
5. Start `yago-crawler` only after node search acceptance passes. Confirm its connected state and new logical session, then prove manual and web-ingest crawl-order progress, DDGS materialization under the stored operator policy, and absence of a repeating lease-loss or reconnect loop.

For rollback to v0.0.52, stop both services, install the exact published v0.0.52 package, and start the node before the crawler. The index remains in the same writer generation and segment format, so no rebuild is expected. Rollback restores the observed late fuzzy-enumeration behavior.

## Known limitations

- Production success remains unconfirmed until the published v0.0.53 Debian package is deployed and genuinely new sequential and synchronized local searches complete within the operator budget before the crawler is started.
- One active Bleve field-dictionary `Next` call and normal close cannot be interrupted by this boundary. The production-copy overrun was 18.5 milliseconds beyond the 125-millisecond context; a future upstream context-aware dictionary API could reduce that bound.
- One four-processor process is not validated for hundreds of complete HTTP requests with live projection, evidence, peer work, and response encoding. Sustained hundreds-request service needs separately implemented and measured horizontal read capacity with independent processors and independently owned index generations.
- Same-host processes sharing the current four processors are not additional capacity. Multiple processes must not open one live mutable Scorch directory. Immutable index-generation distribution and replica-aware routing are not part of this release.
- Bleve v2.6.1 and zapx v17.2.3 correct the known empty-middle-chunk writer class, and deployed releases show no recurrence of its corrupt-frequency OOM symptom. They do not add an independent decoder allocation bound before allocating locations from decoded frequency data.
- DDGS engines are external and can throttle, change markup, or return an honest empty result. Fallback remains disabled unless an administrator explicitly enables the applicable mode.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
