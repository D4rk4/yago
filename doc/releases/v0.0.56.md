## Abstract

Yago v0.0.56 restores admin-enabled DDGS fallback for requests that require safe search. The provider previously returned web rows without safety evidence, so the common fail-closed boundary removed every row even when an engine had applied a filter. Safe requests now force the strongest documented filter, exclude engines that cannot enforce it before egress, and retain provider-filter evidence through normalization and caching. Unknown web rows remain rejected; local and peer rows cannot claim this evidence. A fresh isolated full-stack node returned five RFC 9562 results with safe search enabled and disabled. APIs, formats, settings, dependencies, and deployment topology are unchanged. No data migration or index rebuild is required.

## Changes

### Require provider safety evidence for web results

An isolated pre-fix full-stack node reproduced the defect without opening production data or a copied database. With DDGS fallback enabled, an RFC 9562 query returned five web rows when `safe_search=false`. The same query returned an incomplete zero-row answer when `safe_search=true`, although the selected engine had fetched and accepted ten rows. The external provider result carried `SafetyUnknown`, and the common fail-closed safe-search boundary correctly refused unknown web content.

A safe request now overrides the operator's provider preference only for that request and requires the strongest documented adult-content filter. DuckDuckGo HTML and Lite use strict `kp=1`, Brave uses `safesearch=strict`, and Mojeek uses `safe=1`. The auto race excludes an engine without an implemented strict-filter contract. An explicitly selected unsupported backend fails before egress and becomes the established recoverable web partial failure. Requests without safe search keep the configured provider preference. DuckDuckGo's ordinary modes are corrected to moderate `kp=-1` and off `kp=-2`; Brave's moderate mode is sent explicitly.

Rows fetched under the required filter carry a distinct internal rating through bounded normalization, cache storage, constraint verification, and conversion to the common search result. Filtered and unfiltered requests have separate cache identities. The common boundary accepts the rating only from the external web source. Unknown web rows remain rejected, and a local or peer row carrying the same value is rejected. Internal provenance remains `ddgs`, human-facing provenance remains `web`, and Tavily-compatible responses gain no provider field.

Permanent tests prove the request override and ordinary configured mode, corrected engine parameters, filtered and unfiltered cache separation, evidence preservation during normalization, refusal before egress for an unsupported backend, acceptance of genuine web evidence, and rejection of the same rating on local and peer rows. The corrected fresh full-stack synthetic returned HTTP 200 and five web rows with safe search both enabled and disabled. Every disposable process, binary, data directory, and response file was removed after the test.

ADR-0077 records the fail-closed provider-evidence boundary and amends ADR-0019 and ADR-0021. FTR-202 records the implemented behavior. The release audit matched all 78 numbered ADR files to 78 unique index targets. Seventy-four live decisions are Accepted, ADR-0007, ADR-0030, and ADR-0035 are Superseded, and ADR-0000 is the non-decision template. The previously delayed ADR-0063 remains implemented by FTR-187's bounded post-open word-filter maintenance and its bidirectional and lifecycle tests. No accepted or queued ADR implementation remains knowingly outstanding.

The architecture continues to treat hundreds of simultaneous deadline-bound reads as a horizontal capacity requirement. Fast reads remain observation-only and deadline-bounded. A future read tier must give each replica independent processor and I/O capacity, an independently owned immutable search generation, a query-ready document projection, bounded admission, freshness-aware routing, queue-inclusive latency validation, and N+1 capacity. Multiple processes must not share one live mutable Scorch directory. This release does not introduce that runtime service boundary or claim hundreds-request capacity from one four-processor node.

## Known limitations

- Fresh authenticated production verification of the safe fallback requires an existing operator credential. The release does not bypass, reset, or disclose authentication state; isolated provider and full-stack checks are the pre-deployment evidence.
- A safe request has fewer eligible engines because an engine without an implemented strict-filter contract is excluded. External engines can throttle, change markup, return an honest empty result, or fail to filter content perfectly. The local boundary preserves evidence and stays fail-closed; it cannot independently inspect an external provider's complete corpus.
- DDGS fallback remains disabled unless an administrator explicitly enables the applicable mode. An explicitly selected unsupported backend yields a recoverable web partial failure for safe requests.
- One four-processor process is not validated for hundreds of complete HTTP requests with projection, evidence, peer work, and response encoding. Sustained hundreds-request service needs separately implemented and measured horizontal read capacity with independent CPU, I/O, immutable generations, query-ready projections, freshness-aware routing, queue-inclusive admission, and one-replica-loss capacity.
- Same-host processes sharing the current four processors are not additional capacity. Multiple processes must not open one live mutable Scorch directory. Immutable generation distribution and replica-aware routing are not part of this release.
- Issue #3 remains open because a point-in-time resident-memory value does not establish growth or pressure. Use the existing Admin memory split together with cgroup events and repeated observations before attributing file-backed residency or anonymous memory.
