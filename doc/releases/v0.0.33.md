## Abstract

YaGo v0.0.33 corrects a storage-maintenance outage caused by ordinary records in a bbolt structural root. Shard growth treated every top-level entry as a bucket and dereferenced a nil bucket for each record, so the reference node entered a seven-restart crash loop. The node now enforces a bucket-only root before commit, isolates unexpected records into durable quarantine, restores only provable RWI postings without overwriting live conflicts, and resumes safely after interruption at any recovery phase. Split, compaction, and migration return errors instead of panicking. No protocol, API, configuration, dependency, listener, or deployment topology changes.

## Changes

### The structural root is now an enforced boundary

Every application write transaction validates the bbolt top-level tree immediately before commit. A top-level entry that is not a bucket refuses the transaction with a structural-root error. This closes the repository-side creation path even if a future writer accidentally targets the transaction root: an invalid shape cannot be committed through the vault boundary.

The same rule now protects retained legacy migration, shard splitting, and compaction. Those paths check the shape explicitly and return a diagnostic error instead of passing a nil bucket to bbolt iteration or compaction. The direct nil checks remain at each maintenance edge so a missed startup intervention cannot become another panic.

### Startup repairs the evidenced RWI shape without guessing

Before word-filter construction and before serving, every shard moves ordinary root values into an internal flat quarantine in the same transaction that removes them from the structural root. The quarantine identity is a checksum of a versioned envelope containing the original key and stored bytes, so retrying isolation cannot silently replace different evidence.

A quarantined value qualifies for replay only when all three independent facts agree: its key is exactly one YaCy word hash followed by one URL hash, its decoded stored bytes are a valid RWI posting, and that posting's URL hash equals the key suffix. The original stored bytes are written to the shard selected by the current routing manifest. A missing posting is inserted and increases collection length once; an exact live copy is released without changing length; a different live posting is never overwritten. Invalid envelopes, unrecognized values, and conflicts remain verbatim in quarantine.

Destination replay commits and is synchronized before quarantine release. Recovery therefore converges after interruption following isolation, destination commit, or release. A later pass sees an exact destination copy and completes without applying length twice. Runtime recovery before split or compaction also feeds restored word keys into the existing live filter side set.

One stable WARN record, `vault root record recovery completed`, reports isolated, restored, already-present, conflict, and retained totals whenever an intervention has something to report. A nonzero retained total records preserved evidence and does not by itself prevent startup.

### Incident finding

The reference `v0.0.32` node crashed seven times in automatic shard growth because `Tx.ForEach` returned a nil bucket for an ordinary root value and the split copier dereferenced it. Read-only inspection found 58 proper top-level buckets and 2,104 ordinary values in shard 1. Every ordinary value was a valid stored RWI posting with a 24-byte word-hash-plus-URL-hash key, and all routed to shard 1 under the historical eight-shard layout. At inspection time, 1,478 were absent from the live `rwi` bucket, 457 were exact copies, and 169 conflicted with a live value.

Preserved backups from 2026-07-11 and 2026-07-16 contain no ordinary root values. The malformed shape already caused compaction panics on 2026-07-23 under `v0.0.21` and on 2026-07-24 under `v0.0.22`; releases after that did not create it. Repository-history review found no application writer that targets the transaction root, and the affected cursor paths copied transaction-backed keys before retaining them. The host is a QEMU guest on XFS, and its unclean 2026-07-19 disappearance followed a kernel storage/ATA soft lockup and required XFS log recovery. That is the strongest evidenced creation event. The exact hypervisor or virtual-device failure below the filesystem boundary remains unconfirmed; this release does not assign a more specific cause than the evidence supports.

The code regression was independent of that lower-layer event: the vault had no structural-root invariant or recovery boundary, so an exceptional disk shape survived normal commits and later turned two maintenance paths into panics. This release closes that software failure chain.

## Compatibility

- YaCy wire endpoints, Tavily-compatible endpoints, public search surfaces, request and response schemas, storage routing, RWI encoding, package paths, image names, ports, listeners, services, and deployment topology are unchanged.
- No environment variable, Admin setting, or dependency changes. Docker Compose and systemd examples therefore require no surface update.
- The only new persistent object is the internal quarantine bucket in a shard that required intervention. Older releases tolerate unknown top-level buckets, but they neither validate nor replay this evidence.
- Successful recovery can increase the visible RWI collection length when a proven posting was missing. Exact duplicates do not change it, and conflicts are never substituted.
- Operators may see one new WARN recovery record during startup or maintenance. Ordinary healthy starts emit no such record.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.33 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.33`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Poll readiness rather than assuming it: recovery precedes the normal sequential shard open and word-filter work, which can take several minutes on a large vault. Inspect the recovery WARN totals, confirm that retained records are only the expected conflicts or unknown evidence, verify the exact version, `/health`, `/ready`, configured listeners, and absence of a split or compaction panic.
5. Start `yago-crawler` only after node readiness. Verify its exact version, control and ingest connections, a current heartbeat, crawl progress, and absence of a repeating lease-loss loop.
6. Keep production verification observation-only after service startup.

For rollback after a successful v0.0.33 recovery, stop crawler and node, reinstall the v0.0.32 package, start and verify the node, and then start the crawler. The older binary leaves the quarantine bucket untouched and continues using the restored postings. If v0.0.33 fails before recovery completes, preserve the vault and existing backups and diagnose that failure before reinstalling v0.0.32; the older splitter cannot safely consume unresolved ordinary root values.

## Known limitations

- Recovery is deliberately limited to the evidenced ordinary-root shape. It does not claim to repair arbitrary bbolt page, metadata, filesystem, or block-device corruption.
- Invalid, malformed, or conflicting records remain in quarantine. The node reports their total but does not choose among conflicting postings or delete forensic evidence automatically.
- The exact failure below the guest filesystem that created the historical root records is unconfirmed. The new invariant prevents a repository writer from committing the same shape, and startup and maintenance contain and recover the known shape, but an operator should still investigate any recurring host storage fault.
- A large vault still builds its word filters before opening listeners. This release prevents the maintenance panic; it does not remove the existing cold-start interval.
