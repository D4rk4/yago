## Abstract

YaGo v0.0.29 adds a filter for when this node first saw a page, and stops the
content-cluster index from parsing the same record twice. A third of indexed
documents carry no publication date at all, so `published_date` could never
reach them; `first_seen_start` and `first_seen_end` bound discovery time
instead, and publication keeps meaning publication. On the write path, every
stored fingerprint was decoded once by the storage codec and again by its
reader, and the posting rule rebuilt a shingle vector of up to four thousand
values to ask whether it was empty. Measured on the reference deployment, that
was about sixteen per cent of node CPU. No storage format changes.

## Changes

### A first-seen window, separate from publication

`POST /search` accepts `first_seen_start` and `first_seen_end`, inclusive
`YYYY-MM-DD` dates whose end bound covers the whole end day. They bound
`documentstore.FirstSeenAt` -- when this node first stored the document -- and
are a yago extension with no upstream Tavily equivalent.

The reason is a measured gap. Two thirds of indexed documents carry a
publication date; the remaining third is download pages, landing pages, category
listings, shop product pages, and documentation that genuinely publishes no
date. A `published_date` filter cannot reach that third at all, and the honest
answer for such a document is that its publication date is unknown, not that it
is the day the crawler arrived.

`searchcore.Request` and `searchindex.SearchRequest` carry `MinFirstSeen` and
`MaxFirstSeen`; `searchlocal` passes them through; one `allowsFirstSeen`
predicate beside `allowsDocumentDate` applies them to all three retrieval paths
at once, because the memory index, the disk index, and the complete-hits loop
all funnel through `allowsDocument`. A document with no first-seen time does not
qualify under an active bound, matching the rule the document-date filter
already applies to an undated document.

Two silent-corruption sites are closed with it. The bounds join the local
result-cache identity, so a bounded query is never served a cached unbounded
result set, and they join `hasPostFilters`, so the disk hit loop keeps hydrating
past a full page and reports an honest total instead of bleve's unfiltered
count.

The filter is deliberately narrow. `time_range`, `days`, and `topic` keep their
upstream publication-recency meaning and never produce a first-seen bound.
Freshness ranking is unchanged: it decays publication age, and a first-seen-only
request takes the same adaptive profile an unfiltered request takes. No result
field reports the first-seen time, and the window is not exposed on
`/yacysearch.*` or in the Admin console.

First-seen is a property of this node's own index, because peers neither send
nor receive it. Retrieval still runs local-plus-peer, but a served row this node
does not hold cannot be shown to fall inside the window and drops under an
active bound; a window that retains nothing answers HTTP 200 with an empty
result list. A first-seen-bounded request also consults no external web-search
provider, whose rows are never held here and would all drop, and therefore seeds
no crawl URLs from that provider.

### The content-cluster index stops parsing every record twice

The fingerprint keyspace was registered with a JSON codec over
`json.RawMessage`. Decoding into a `json.RawMessage` runs `json.Unmarshal` over
the whole document -- scanning and validating every byte -- and returns a copy
of the same bytes, which the reader then parsed a second time to fill its
struct. A stored fingerprint averages 18.7 KB on the reference deployment
because it carries the shingle vector, so every read paid a full scan for
nothing. A passthrough codec replaces it and still copies, keeping the lifetime
contract every caller already had: the bytes underneath may be a window into the
storage engine's mapping, valid only inside the enclosing transaction.

The posting rule was the largest consumer of those reads. Preparing one page
re-reads every member of every posting bucket it belongs to -- up to nine
buckets of up to 256 members -- and each member was decoded in full so that
`postingMatches` could compare a content hash, a fingerprint, and whether the
shingle vector was empty. It now decodes a reduced shape whose shingle field
records presence without building the vector, which allocates a constant amount
regardless of how many shingles the record holds.

Attaching a record to a content cluster also made two passes over the cluster's
members: the resolution pass chose a representative, that choice was discarded,
and a second pass re-read every member to choose it again. The resolution pass
is authoritative -- normalization already stores its choice unchanged -- so the
attached record is folded into it instead.

## Compatibility

- No environment variable, Admin setting, route, response field, public schema, listener, port, service, image name, package path, Bleve mapping, document encoding, storage format, or deployment topology changes. No contract or wire-format change. No dependency change.
- Two additive request fields on `POST /search`: `first_seen_start` and `first_seen_end`. A client that sends neither sees no change in behaviour. A malformed or reversed window is refused with the same detail-only HTTP 400 envelope `start_date` and `end_date` already use.
- The stored-candidate projection gains two JSON keys, `f` and `fc`. Adding a key does not change the Bleve field mapping, so no shard is judged stale and nothing is rebuilt. Payloads already on disk carry no first-seen key; an absent key decodes to the same zero time a document with no first-seen time carries, so such a payload declines a first-seen-bounded request and the stored document answers it instead. That costs one document read per hit until the shard is rebuilt in the normal course of indexing.
- The content-cluster changes are read-path only. The bytes written to the fingerprint keyspace are identical to those v0.0.28 wrote, and the previous release reads everything this one writes.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.29 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.29`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify the exact version, `/health`, `/ready`, configured listeners, and current logs.
5. Start `yago-crawler` after node readiness. Verify its exact version, control and ingest connections, a current heartbeat, and absence of repeating lease-loss output.
6. Keep production verification observation-only.

For rollback, stop crawler and node, reinstall the v0.0.28 package, start and verify the node, and then start the crawler. No index rebuild or data restore is required. The storage format is unchanged in both directions: the fingerprint keyspace holds the same bytes either release writes, and the older node ignores the two additive stored-candidate keys the way it already ignores an unknown optional field. A client using `first_seen_start` or `first_seen_end` loses the filter on rollback -- the older node does not recognise the fields -- and the older release does not restore the read-path savings.

## Verification

- `make verify` on the release tree: tidy, format, vet, lint, architecture, race tests, build, and coverage at exactly 100 percent of statements in all six modules (`yagonode` 46905, `yago-crawler` 12051, `yagocrawlcontract` 1265, `yagomodel` 923, `yagoproto` 517, `yagoegress` 59).
- Mutation testing on every behavioural claim this release makes. Nine mutations of the first-seen predicates -- both bounds, the inclusive edges, the is-set guard on an open end, the refusal of an undated document, filtering when no bound is set, the range validator, and the web-provider suppression -- all fail a test. Seven mutations of the reduced posting decode, including restoring the vector materialization, all fail. Three mutations of the passthrough codec, including returning the storage slice instead of a copy, all fail. Six mutations of the cluster attach fold all fail.
- Two of those sweeps found gaps in the tests written alongside the code rather than in the code. The conjunct that makes the first-seen refusal conditional on an active bound survived removal: without it the same line drops every peer and web row from an ordinary `published_date` query. The seed that makes an empty cluster take its first member survived removal because the fixture's quality score beat the zero value regardless. Both now have a test that fails when the guard is removed.
- The cluster attach fold was additionally checked against the algorithm it replaces over 400 randomized cluster states, covering absent members, members belonging to another cluster, empty clusters, and ties; the differential check itself was confirmed non-vacuous by inverting the comparison, which fails it on the second state.
- Decode cost was measured against the size distribution production actually stores rather than a chosen size. 49421 fingerprint records were read from one of the eight vault shards on the reference deployment: shingle vectors average 902 values, median 497, and the stored record averages 18.7 KB. On that distribution the passthrough codec removes 21x the work of the JSON codec it replaces, and the reduced posting decode is 1.46x faster while allocating 108x less. The profile attributes 14.8 seconds of a 131.5-second sample to the codec and 23.8 to the record parse, so the two changes together account for about sixteen per cent of node CPU.
- Pinned Dockerized scanners. Semgrep 1.168.0 `scan --config auto --error`: clean. Trivy 0.72.0 filesystem scan for HIGH and CRITICAL vulnerabilities, secrets, and misconfigurations: clean across all module manifests and both Dockerfiles. Trivy image scans of the built `yago-node` and `yago-crawler` images with image-config secret and misconfiguration scanners: both clean.
- Local Docker live lifecycle gate: `TestIndependentServiceRestartsRecoverCrawlerSessions` passed in 51.32 seconds against images built from this tree, exercising independent node and crawler restarts and crawl-session recovery.
- Release issue review: no open issues in the repository.

## Known limitations

- The read-path savings are projected from a production CPU profile and a benchmark over the measured record-size distribution. They have not been re-measured on the reference deployment after this release; the profile that established them was taken before the changes, and confirming the effect requires a second profile after deployment.
- A peer result cached into the local index by the remote-index cache is a stored document, so it receives a first-seen time of the moment it was cached. A first-seen window therefore also returns metadata-only stubs that earlier searches wrote, not only pages this node crawled. That follows from the definition -- the node did first see the URL then -- but it means a bounded query can return rows whose first-seen time is an artifact of a search rather than of crawling.
- The corpus-signal refresh is untouched. It rescans every stored document every ten minutes and fully decodes each one, including its extracted text, and accounts for more node CPU than everything this release changes. It is correctly a paged background read and blocks no writer, but it is the largest remaining consumer.
- The remaining write-gate contributors from v0.0.27 are still untouched: the RWI intake transaction is unbounded in size, the peer-reputation writer scans every peer inside its write transaction, the transfer tally takes a writer's mutex on its read path, and overflow trimming runs on the synchronous hello path. Peer-roster observation failures continue at roughly 250 per twenty minutes on the reference deployment.
- Two further reductions in fingerprint read cost were designed and deliberately not taken. Moving the comparison fields into a separate small keyspace would let the posting rule read a few hundred bytes instead of the whole record, but its benefit shrank once the double decode was removed, and it introduces a synchronization surface between two stores. Packing the shingle vector as binary instead of a JSON array of decimal numbers would roughly halve both the parse and the 7.4 GB the fingerprint keyspace occupies, but it changes the stored format and so cannot be rolled back within one release.
- Prometheus metrics are disabled on the reference deployment by a persisted setting that overrides the environment default, and enabling them requires a node restart. Storage read-deferral and ingest-absorption counters therefore remain unreadable there, and indexing throughput can only be observed through the index document count and the crawler's own metrics listener.
