## Abstract

YaGo v0.0.30 makes a lost web provider say why, and stops a first-seen window
from being read as a lost source. Both provider-failure records were written at
Debug while a node runs at Info, so on the reference deployment, where the
provider failed on half of all searches, the journal carried a count and no
cause. Separately, a first-seen window is applied inside the index rather than
after retrieval, so the availability rule saw the caller's own filter as a
source that did not answer and refused with HTTP 409 the requests the
specification says answer 200 with an empty list.

## Changes

### A lost web provider now says why

The two records that mark a lost provider stage were written at Debug. A node
runs at Info, so neither reached the journal. What remained was an aggregate
outage warning carrying `webSearchFailureReason`, whose default arm collapses
every distinct upstream error into `backend`. On the reference deployment 122 of
246 searches lost the provider and 31 outage warnings were recorded in six
hours, with no way to tell a blocked scrape from a throttled one or from a
changed page.

Both records are now written at Info. The per-engine record is the one that
carries the diagnosis: it names the engine, reports whether it was rate limited,
and gives the number of results fetched against the number that survived
acceptance.

The failing error itself is deliberately not logged. Its text contains the
request URL, and the request URL contains the submitted query, so attaching it
would publish what the caller searched for. The first draft of this change did
attach it, and the existing privacy test refused the build.

This is the cause behind a report that web results seed no crawl. The seeding
path is enabled, wired into both the fallback and the parallel searcher, and
fires whenever the provider returns rows; it published nothing because the
provider returned nothing. That was equally true before v0.0.29 -- the reference
deployment published no seed in the three hours preceding that upgrade either --
so this release makes the failure legible rather than changing the seeding path.

### A first-seen window is no longer read as a lost source

Availability is scored on what the sources returned rather than on what survived
the caller's filters. That is what keeps an over-narrow date or domain request
from being reported as a failure: those filters are applied after retrieval, so
the count the rule sees still reflects what the sources answered.

A first-seen window is applied inside the index during retrieval, so rows it
excludes never reach that count. A node in a live swarm almost always loses at
least one source, so the pair -- zero retained, one source lost -- refused with
HTTP 409 whenever the window happened to keep nothing, which is exactly the case
the specification says answers HTTP 200 with an empty result list.

The availability rule is therefore not applied to a first-seen-bounded request.
The exemption is scoped to that filter alone; every other request shape keeps
the refusal unchanged.

## Compatibility

- No environment variable, Admin setting, route, request field, response field, public schema, listener, port, service, image name, package path, Bleve mapping, document encoding, storage format, or deployment topology changes. No contract or wire-format change. No dependency change.
- One status-code change, narrowed rather than widened: `POST /search` with `first_seen_start` or `first_seen_end` no longer returns HTTP 409 when the window retains nothing. It returns HTTP 200 with an empty result list, which is what the published specification for the field already stated. A request without a first-seen window is unaffected, including the HTTP 409 it returns when nothing was retrieved and a source was genuinely lost.
- Two log records move from Debug to Info: `web-search fallback provider failed` and `web-search engine attempt`. An operator filtering on Debug sees no change; an operator reading Info now sees one record per lost provider stage and one per engine attempt. Neither record contains the submitted query.

## Upgrade and rollback

1. After the immutable tag workflow succeeds, download the architecture-matching v0.0.30 Debian package. Verify its GitHub artifact attestation against repository `D4rk4/yago`, workflow `.github/workflows/release.yml`, tag ref `refs/tags/v0.0.30`, and the tagged source commit before stopping either service.
2. Follow the target's data-protection policy. Generic bare-metal nodes take one coordinated stopped backup. The documented `root@yagoseek.dev` exception preserves every existing archive under `/opt/yago/backups` and creates no new pre-upgrade backup; stage the verified package under `/opt/yago/releases`.
3. Stop `yago-crawler` and then `yago-node`. Install the package with `dpkg -i` and confirm that package installation did not start either service automatically.
4. Start `yago-node` first. Verify the exact version, `/health`, `/ready`, configured listeners, and current logs. On an index of this size the vault word filter is built before the listeners open; on the reference deployment that took 520 seconds, and readiness should be polled rather than assumed.
5. Start `yago-crawler` after node readiness. Verify its exact version, control and ingest connections, a current heartbeat, and absence of repeating lease-loss output.
6. Keep production verification observation-only.

For rollback, stop crawler and node, reinstall the v0.0.29 package, start and verify the node, and then start the crawler. No index rebuild or data restore is required; no storage format changed in either direction. The older release returns HTTP 409 again for a first-seen window that retains nothing, and returns both provider records to Debug.

## Verification

- `make verify` on the release tree: tidy, format, vet, lint, architecture, race tests, build, and coverage at exactly 100 percent of statements in all six modules (`yagonode` 46907, `yago-crawler` 12051, `yagocrawlcontract` 1265, `yagomodel` 923, `yagoproto` 517, `yagoegress` 59).
- Mutation testing on both changes. Removing the availability exemption, disabling the availability rule outright, and returning either log record to Debug each fail a test.
- The exemption test was itself corrected by that sweep. Its first fixture let retrieval return a row that the window dropped afterwards, which leaves the availability count non-zero and proves nothing; removing the exemption kept the test green. The fixture now returns nothing from retrieval, which is the shape a live node produces, and the mutation fails.
- The provider-logging change was corrected by an existing test. Its first draft attached the failing error, whose text carries the request URL and therefore the submitted query; `TestUnavailableLoggingDoesNotExposeSubmittedQuery` failed the build. The record now carries the engine, its rate-limit state, and its result counts, and the new test asserts both that those fields survive at Info and that the query does not appear.
- Diagnosis evidence from the reference deployment: 122 of 246 searches since the previous restart recorded a lost provider; 31 outage warnings in six hours, 23 with reason `backend` and 8 with `deadline`; zero crawl seeds published in the twelve hours after the v0.0.29 upgrade and zero in the three hours before it.
- Pinned Dockerized scanners. Semgrep 1.168.0 `scan --config auto --error`: clean. Trivy 0.72.0 filesystem scan for HIGH and CRITICAL vulnerabilities, secrets, and misconfigurations: clean. Trivy image scans of the built `yago-node` and `yago-crawler` images with image-config secret and misconfiguration scanners: both clean.
- Local Docker live lifecycle gate: `TestIndependentServiceRestartsRecoverCrawlerSessions` passed against images built from this tree.
- Release issue review: no open issues in the repository.

## Known limitations

- This release makes the provider failure legible; it does not fix it. The reference deployment still loses the provider on roughly half of its searches, and until the cause recorded by the new per-engine record is acted on, web results remain sparse and the crawl seeding they feed stays idle.
- The availability exemption is scoped by request shape rather than by evidence. A first-seen-bounded request that genuinely lost a peer now answers HTTP 200 with whatever survived, and the Tavily response carries no provenance, so the caller cannot tell a complete answer from a narrowed one. Counting the window's removals separately from the sources' answers would let the rule apply to both, and is the change this release does not make.
- The first-seen window itself is unchanged and behaves as v0.0.29 documented: rows this node does not hold drop under an active bound. On a node whose answers for a given query come mostly from peers, such a window can therefore return very few rows or none, and that is the filter working rather than failing.
- A peer result cached into the local index receives a first-seen time of the moment it was cached, so a first-seen window also returns metadata-only stubs written by earlier searches.
- The corpus-signal refresh, the peer-roster write contributors from v0.0.27, and the two deferred fingerprint-read reductions described in the v0.0.29 memo are all untouched.
